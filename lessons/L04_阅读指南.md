> 建议先跑演示脚本再读讲义：看过一轮一轮的真实 messages，讲义里的概念就都有了画面。


## 第一轮 · 原理

### [ ] 第 1 步：先运行演示脚本（20 分钟）
```powershell
python walkthroughs/L04_tool_loop.py --offline   # 第 1、2 步：离线
python walkthroughs/L04_tool_loop.py             # 全部 5 步：约 $0.002
```
- **看什么**
  - 第 1 步：模型看到的工具说明书长什么样。它就是一段 JSON，也是 prompt 的一部分。
  - 第 2 步：`eval` 真的执行了代码；AST 语法树长什么样；哪些表达式被拒绝、错误信息怎么写。
  - 第 3 步：**每一轮发出去几条消息、分别是什么角色**。第 2 轮比第 1 轮多了哪 3 条？
  - 第 4 步：模型看到错误信息之后做了什么。
  - 第 5 步：assistant 消息里多了 `reasoning_content`；去掉它，这次的服务端怎么反应。
- **易错点**：第 4 步的历史是**手工构造的**（假装模型写了带逗号的表达式）。它演示的是"拿到错误之后会怎样"，不是"模型会不会写错"。

### [ ] 第 2 步：讲义 §1–§2　为什么需要工具，function calling 的本质（30 分钟）
- **知识点**
  - 两个问题要分开：不知道数（知识，L05）和算不对数（计算，本课）；FinQA 用"给定上下文"排除前者
  - LLM 算数的三个弱点：数字切分不规则、生成顺序与进位顺序相反、开方类运算没有逐位算法
  - 模型只输出调用意图；`finish_reason="tool_calls"`；`arguments` 是字符串
  - 四个要点：tools 每次都发、调用请求放回历史、每个调用一条 tool 消息且用 `tool_call_id` 对号、并行调用
  - `tool_choice` 的取值，以及 thinking 模式下的限制
  - thinking + 工具：`reasoning_content` 要传回（文档 vs 实测）
  - 模型怎么"学会"调用工具：chat template 渲染说明书 + 训练出的特殊格式 + 服务端解析
- **易错点**
  - 以为模型会自己执行函数、自己访问网络。**它只会生成文本。**
  - 把 `arguments` 当成 dict 直接用：它是字符串，而且可能不合法。
  - 下一轮只发 tool 消息，忘了先把 assistant 的调用请求放回历史：模型会看不懂这些结果是什么。
  - 两个调用只回传一条结果，或者 `tool_call_id` 写错。
  - 文档和实测不一致时，依赖实测到的宽松行为。

### [ ] 第 3 步：讲义 §3–§4　说明书设计与安全（25 分钟）
- **知识点**
  - 说明书从函数签名 + docstring 自动生成；`create_model` 一身两用（生成 schema、校验参数）
  - 描述要写清"何时用、怎么写、不要写什么"，参数描述里给例子
  - 参数的三关校验；错误信息回传给模型，而不是抛异常
  - 说明书每次都要发送，也是成本
  - `eval` 的危险；AST 白名单与"默认拒绝"；白名单也管语义（`%`、千分位逗号）；资源限制（float、长度、嵌套）
- **易错点**
  - 描述只写"Calculator."：模型不知道什么时候该用。
  - 错误信息只写 "invalid input"：模型不知道该怎么改。
  - **用黑名单**（禁止 `import`、`os`……）代替白名单：总有你没想到的写法。
  - 只考虑"危险代码"，忘了"合法但卡死程序"的表达式（`9 ** 9 ** 9`）。
  - 忘了 `bool` 是 `int` 的子类：`True + 1` 在 Python 里等于 2。

### [ ] 第 4 步：讲义 §5　手写工具循环（20 分钟）
- **知识点**
  - 循环的 4 步：请求 → 回复放回历史 → 没有调用就结束 → 逐个执行并回传
  - 轮数上限；达到上限时这次尝试算失败，从头再试
  - `generate` 参数：结构化输出（校验 + 重试）和工具循环的组合
  - `attempts` 和"调用模型次数"是两个不同的数
  - **JSON mode 会压制工具调用**；工具循环默认不开 JSON mode
- **易错点**
  - 没有轮数上限。
  - 在循环里直接修改调用方传进来的 messages 列表（我们先 `list(messages)` 复制一份）。
  - 以为 JSON mode 越多越保险。开着它，模型几乎不用工具。
  - 统计成本时只算"尝试次数"：一次尝试里可能有好几次调用。

### [ ] 第 5 步：讲义 §6　FinQA 评测集（15 分钟）
- **知识点**
  - 两份标准答案互相核对（`answer` vs `exe_ans`），能发现什么、发现不了什么
  - dev / test / train 分别来自 FinQA 的三个文件，互不重叠
  - 按计算步数分层，每层一样多（代价：整体分数不代表原始分布）
  - 单位跟着片段走；`sign_error` 与 `sign_agnostic`
  - 新增字段取默认值时不写出，旧评测集文件逐字节不变
- **易错点**
  - 把一致性检查当成"标准答案一定对"：程序写错时，两份照样一致。
  - 按比例抽样，多步题太少，看不出计算器对多步题的效果。
  - 给 `EvalItem` 加字段后重新生成所有评测集，旧记录的哈希全部对不上。

## 第二轮 · 代码（自底向上）

依赖关系（箭头表示"用到了"）：

```
cli.py (ask --context-file, eval)
   └──> eval/run.py ──> pipeline/answer.py ──> agent/loop.py ──> tools/registry.py ──> llm/base.py
                               │                    └──> llm/structured.py (Generation)
                               └──> llm/structured.py (call_structured, generate)
tools/__init__.py ──> tools/calculator.py ──> tools/registry.py
scripts/build_evalsets.py ──> eval/datasets.py (parse_finqa_gold)
```

### [ ] ① [src/finagent/llm/base.py](../src/finagent/llm/base.py)（10 分钟）
- **知识点**：`ToolCall`（id、name、arguments 字符串）；`ToolStep`（调用 + 结果 + 是否成功）；`LLMResponse.tool_calls`；`to_message()` 把回复变成 OpenAI 格式的 assistant 消息，thinking 时带上 `reasoning_content`。
- **易错点**：OpenAI 格式里 `tool_calls` 的每一项是 `{"id", "type": "function", "function": {"name", "arguments"}}`，多了一层 `function`。

### [ ] ② [src/finagent/llm/openai_compat.py](../src/finagent/llm/openai_compat.py)（10 分钟）
- **知识点**：`_build_request` 里 tools 怎么放、为什么不传 `tool_choice`；`parse_tool_calls`（没有调用时 SDK 给的是 `None`）；调用记录里只记工具名。
- **易错点**：流式 + 工具目前直接报错。流式时参数是分片到达的，要按 `index` 拼接（作业 4）。

### [ ] ③ [src/finagent/tools/registry.py](../src/finagent/tools/registry.py)（20 分钟）
- **知识点**
  - `tool` 装饰器：`inspect.signature` + `get_type_hints` → `create_model`
  - `_parse_docstring`：Google 风格 docstring 的 Args 段怎么解析（续行怎么处理）
  - `_strip_titles`：去掉 pydantic 自动加的 title，省 token
  - `Tool.run` 的三关校验，每关失败都返回 `"Error: ..."`
  - `ToolRegistry.execute`：不存在的工具名也回传错误
  - `build_registry`：配置里的名字拼错就报错
- **易错点**
  - `except Exception` 一般是坏习惯，这里是有意为之：工具里的任何意外都不能让循环崩溃，所以加了 `noqa` 并写明原因。
  - `create_model` 的字段写法是 `名字=(类型, Field(默认值, description=...))`，必填字段的默认值是 `...`。

### [ ] ④ [src/finagent/tools/calculator.py](../src/finagent/tools/calculator.py) ★（20 分钟）
- **知识点**：`ast.parse(mode="eval")`；`_eval` 递归只认白名单节点；`%` 在解析前就拒绝；`ast.Tuple` 给出"千分位逗号"的提示；所有常量转 float；复数、inf 的检查；`format_number` 的 12 位有效数字。
- **怎么读**：对照 `tests/test_tools.py` 的 `test_evaluate_rejects`，每一行都在测哪种攻击或错误。
- **易错点**
  - 用 `isinstance(node.value, int)` 判断数字却忘了排除 `bool`。
  - `ZeroDivisionError`、`OverflowError` 要转成 `ToolError`，错误信息才能回传给模型。

### [ ] ⑤ [src/finagent/agent/loop.py](../src/finagent/agent/loop.py) ★（15 分钟）
- **知识点**：整个 function calling 机制就在这十几行里。对照讲义 §2.3 的四个要点，找到每一点对应的那一行。
- **易错点**：达到轮数上限时，最后一次回复里还有未完成的调用，`final.content` 里没有答案，所以要设 `hit_max_rounds`。

### [ ] ⑥ [src/finagent/llm/structured.py](../src/finagent/llm/structured.py) + [src/finagent/pipeline/answer.py](../src/finagent/pipeline/answer.py)（15 分钟）
- **知识点**
  - `Generation`、`single_call`、`generate` 参数
  - `attempts` 改成了字段；`tool_steps` 汇总所有工具调用
  - `hit_max_rounds` 时不带历史、从头重试
  - `answer_question` 的 `context` 检查（prompt 里没有 `{{context}}` 就报错）
  - `functools.partial` 先填好除 messages 以外的参数（L01 也用过它）
  - `tool_options` 把配置变成参数
- **易错点**：`render()` 只在"缺变量"时报错，"多给变量"时静默忽略，所以要用 `PromptTemplate.variables` 主动检查。

### [ ] ⑦ [prompts/answer_ctx_v1.yaml](../prompts/answer_ctx_v1.yaml) 和 [prompts/answer_ctx_tools_v1.yaml](../prompts/answer_ctx_tools_v1.yaml)（10 分钟）
- **怎么读**：用 `git diff --no-index prompts/answer_ctx_v1.yaml prompts/answer_ctx_tools_v1.yaml` 看两者的差别，只多了一段计算器说明。
- **知识点**：开卷 prompt 的规则（只用片段里的数、单位跟着片段走、有符号的变化量、至少 4 位有效数字）；为什么没有 few-shot 示例。

### [ ] ⑧ [scripts/build_evalsets.py](../scripts/build_evalsets.py) 的 FinQA 部分 + [src/finagent/eval/datasets.py](../src/finagent/eval/datasets.py)（15 分钟）
- **知识点**：`finqa_context` 怎么拼上下文；`parse_finqa_gold` 的一致性检查；去重；按步数分层抽样；`DIRECTION_WORDS`；`dump_items` 为什么跳过取默认值的新字段。

### [ ] ⑨ [src/finagent/eval/run.py](../src/finagent/eval/run.py) 与 [metrics.py](../src/finagent/eval/metrics.py) 的改动（10 分钟）
- **知识点**：`check_prompt_fits`（在花钱之前报错）；`tool_stats`（工具使用率、出错率、平均调用次数）；`compare_runs` 新增的成本表；`grade_number` 的符号处理；`estimate_cost` 为什么要乘以调用次数。
- **易错点**（本课真实遇到的 bug）：`git_info` 用 `subprocess.run(..., text=True)` 读 git 的输出，没写 `encoding`。中文 Windows 上默认按 GBK 解码，而 git 输出的中文文件名是 UTF-8，只要仓库里有未提交的中文文件（比如刚写好的讲义），评测就会崩溃。修复：写明 `encoding="utf-8"`。**在 Windows 上调用外部程序读文本时，永远写明编码。**

### [ ] ⑩ 测试（15 分钟）
[`tests/test_tools.py`](../tests/test_tools.py)、[`tests/test_tool_loop.py`](../tests/test_tool_loop.py)
- **知识点**
  - `ScriptedClient`：按剧本返回回复的假模型，并记下每次收到的 messages，这样就能**不联网**检查每一轮发出去的消息对不对
  - 用 SDK 自己的类型 `ChatCompletion.model_validate` 构造假响应，测试 `parse_tool_calls`
  - `monkeypatch.setattr("finagent.tracing.log_call", ...)`：测试时不写调用记录
- **易错点**：假模型记录 messages 时要复制一份（`list(messages)`），否则之后的追加会改掉"当时"的记录。

## 第三轮 · 动手、实验、作业

### [ ] 读实验结果（讲义 §7）
- 打开 `runs/eval/` 下 L04 的六份 `report.md`，对照讲义的表格。
- 用 `finagent compare` 自己重现 §7.2 和 §7.3 的比较，注意成本表。
- 在 v0.4 的 `results.jsonl` 里挑 3 道题，看 `tool_calls` 字段：模型写了什么表达式？

### [ ] 运行命令（讲义 §9）
- `finagent ask --context-file` 需要一个文本文件，可以从 `evalsets/finqa.jsonl` 里复制一道 dev 题的 `context` 字段。

### [ ] 作业（讲义 §10）
- **作业 1（标注审计）**：只看 dev。先独立判断，再看讲义 §7.6 的 4 个例子是否在你的清单里。
- **作业 2（thinking vs 计算器）**：thinking 时 `max_tokens` 要调大；比较时要同时看准确率、花费和延迟。
- **作业 3（第二个工具）**：先写测试，再写工具。
- **作业 4（选做，流式工具调用）**：先打印原始的 SSE 数据，看清分片的样子再写代码。

## 最容易错的 10 件事（读完之后回来自查）

- [ ] 1. 以为模型会自己执行函数。
- [ ] 2. 把 `arguments` 当成 dict，或者不校验就直接用。
- [ ] 3. 回传结果时忘了先放回 assistant 的调用请求，或者 `tool_call_id` 对不上。
- [ ] 4. 工具出错时抛异常，让整个程序崩溃，而不是把错误回传给模型。
- [ ] 5. 用 `eval()` 计算模型写的表达式，或者用黑名单代替白名单。
- [ ] 6. 工具循环没有轮数上限。
- [ ] 7. 给了工具就以为模型会用：不监控工具使用率，不在 system prompt 里说明。
- [ ] 8. 工具循环里开着 JSON mode。
- [ ] 9. 只跑一次就下"显著"的结论，不重复验证。
- [ ] 10. 相信评测集的标准答案一定对，不做逐题的错误分析。
