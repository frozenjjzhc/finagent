## 1. 为什么需要工具

### 1.1 L03 留下的问题

L03 的 FinanceBench dev 上，数值计算题只有 18% 的准确率。这里面混着两个问题：

- **不知道数**：闭卷时模型不知道某家公司某年的原始数字（知识问题，L05 用检索解决）；
- **算不对数**：就算知道了数字，多步计算也可能算错（计算问题，本课用工具解决）。

要单独研究第二个问题，就得先把第一个排除掉。所以本课换了一个评测集 **FinQA**：每道题都附带一页财报（文字 + 表格），答案需要的数字都在里面。这种设定叫**给定上下文**（oracle context），相当于"检索永远正确"的理想情况。

### 1.2 LLM 为什么可能算不好数

先说结论：**现代大模型的四则运算已经相当好，但仍有三类弱点。**

1. **数字的切分方式不规则。** 模型看到的不是一个个数字，而是 token。以 GPT-4 的分词器为例，数字按最多 3 位一段、从左往右切："1234567" 被切成 "123"、"456"、"7"。做加法时，个位对个位的对齐关系就被打乱了。不同模型的切法不同，有的模型把每个数字单独切开，L08 你会亲眼看 Qwen 是怎么切的。
2. **生成顺序和计算顺序相反。** 模型从左往右一个 token 一个 token 地写，而乘法、加法的进位是从右往左的。要写出 5829 × 5735 结果的**第一位**，模型必须在一次前向计算里"心算"完整个乘法。模型写 reasoning（先写算式和中间结果，就像草稿纸）能缓解这个问题，这也是 L02 让 reasoning 排在第一个字段的原因之一。
3. **没有逐位算法的运算。** 开方、分数次幂（比如 5 年复合增长率要开 5 次方）没有简单的逐位步骤，模型只能"估"，结果常常看起来差不多，但小数点后几位是错的。

**例子**：我们的算术探针（§7.1）里，flash 心算"(179942 / 63075) 开 5 次方"这类 CAGR 题，10 道只对了 6 道。错的答案像 15.86（正确是 15.8682）、24.45（正确是 24.3147）：看起来很像对的，正因如此才危险。

### 1.3 解决思路

让模型做它擅长的事（理解题意、从表格里找数、列出算式），把它不擅长的事（精确计算）交给程序。这就是 **tool use**。计算器只是开始：L07 的检索工具、L15 的各种 API，用的都是同一套机制。

## 2. function calling 的本质

### 2.1 模型只输出"调用意图"

最重要的一句话：**模型不执行任何东西。** 它只是在回复里说"我想调用 calculate，参数是这个"，执行、回传结果，全是你的代码做的。

模型的一次回复可能是这样的（`finish_reason` 是 `"tool_calls"`，不是 `"stop"`）：

```json
{
  "role": "assistant",
  "content": "",
  "tool_calls": [
    {
      "id": "call_00_sHzh...",
      "type": "function",
      "function": {"name": "calculate", "arguments": "{\"expression\": \"(5829 - 5735) / 5735 * 100\"}"}
    }
  ]
}
```

注意 `arguments` 是一个 **JSON 字符串**，不是对象。模型生成的就是一段文本，它可能不是合法的 JSON，可能漏参数、传错类型。所以你必须自己解析、自己校验（§3.3）。

### 2.2 一次完整的来回

以"2019 年和 2018 年的收入增长率分别是多少"为例（演示脚本第 3 步的真实输出）：

```
第 1 轮  我们 → 模型：system + user（表格和问题） + tools（计算器的说明书）
         模型 → 我们：finish_reason="tool_calls"，一次请求了两个调用：
                      call_00  calculate("(5829 - 5735) / 5735 * 100")
                      call_01  calculate("(5735 - 5102) / 5102 * 100")
执行     我们在本地算出 1.63905841325 和 12.4068992552
第 2 轮  我们 → 模型：system + user + [assistant 的调用请求] + [tool: call_00 的结果] + [tool: call_01 的结果] + tools
         模型 → 我们：finish_reason="stop"，"Net revenue grew about 1.64% in 2019 and 12.41% in 2018."
```

第 2 轮发出去的 messages 长这样：

| 角色 | 内容 |
|---|---|
| system | 只根据表格回答，每一步计算都用 calculate |
| user | 表格 + 问题 |
| assistant | （请求调用）call_00 → calculate(...)；call_01 → calculate(...) |
| tool | （call_00 的结果）1.63905841325 |
| tool | （call_01 的结果）12.4068992552 |

### 2.3 四个要点

1. **tools 参数每次都要发。** API 是无状态的（L01），模型不记得上一轮有哪些工具，每一轮请求都要带上完整的 tools 和完整的历史。
2. **assistant 的调用请求要原样放回历史。** 模型要先看到"自己请求了什么"，才能理解后面的 tool 消息是什么的结果。
3. **每个调用一条 `role: "tool"` 消息，用 `tool_call_id` 对上号。** 两个调用就是两条 tool 消息。编号对不上，模型就不知道哪个结果属于哪个算式。
4. **并行调用。** 互不依赖的计算，模型会在同一轮里一起请求（上面的例子就是），省掉一轮来回。有依赖的（先算差，再除以基数），可以写成一个表达式，也可以分几轮。

### 2.4 tool_choice

DeepSeek 支持 `none`（不许调用）、`auto`（模型自己决定，有 tools 时的默认值）、`required`（必须调用）和指定某个函数。**thinking 模式下不支持 `required` 和指定函数。** 我们不传，就是 `auto`。

### 2.5 thinking 模式：reasoning_content 要传回去

DeepSeek 文档的要求：带 tools 的请求，之前各轮的 `reasoning_content`（思考过程）必须**完整传回**，"否则 API 会返回 400"。

我们实测了（演示脚本第 5 步）：**故意去掉 reasoning_content，flash 并没有报错**。但我们仍然按文档做，`LLMResponse.to_message()` 总是把它带上。原因有两个：服务端随时可能开始严格检查；而且去掉思考过程后，模型接不上自己上一轮的思路。

**教训**：文档和实际行为不一致时，按文档写代码，同时把实测结果记下来。不要依赖"没有文档说明的宽松行为"。

### 2.6 模型是怎么"学会"调用工具的

模型本身只会生成文本。API 服务端做了两件事：

1. 用 **chat template** 把 tools 的说明书渲染成一段文字，放进模型的输入里（和 system prompt 放在一起）；
2. 模型经过训练，需要调用工具时会输出一种特殊格式的文本（比如 Qwen 用 `<tool_call>{"name": ..., "arguments": ...}</tool_call>`），服务端把它解析出来，变成 API 响应里的 `tool_calls`。

所以 function calling 本质上仍是"生成文本 + 解析"，这就是 `arguments` 可能不合法的根本原因。L08 你会亲眼看到 Qwen 的模板怎么渲染工具；L10、L11 则要用这种格式的数据去训练小模型，教它学会调用工具。

## 3. 工具的说明书（schema）

### 3.1 从函数自动生成

模型看不到函数的代码，只看到说明书：名字、描述、参数（JSON Schema）。手写说明书又长又容易和函数对不上，所以 [tools/registry.py](../src/finagent/tools/registry.py) 的装饰器 `@tool` 从函数本身生成：

```python
@tool
def calculate(expression: str) -> str:
    """Evaluate an arithmetic expression exactly and return the numeric result. Use this tool for ...

    Args:
        expression: One arithmetic expression using plain numbers, + - * / ** and parentheses, ...
    """
```

| 说明书里的 | 来自函数的 |
|---|---|
| `name` | 函数名 |
| `description` | docstring 第一段 |
| 参数的类型、是否必填 | 类型注解、有没有默认值 |
| 参数的 `description` | docstring 的 `Args:` 段 |
| `additionalProperties: false` | pydantic 的 `extra="forbid"` |

实现的关键是 `pydantic.create_model`：用函数签名动态生成一个 pydantic 模型。它一身两用：`model_json_schema()` 生成说明书，`model_validate()` 校验模型传来的参数。L02 学的 pydantic，这里又用上了。

### 3.2 描述怎么写

描述就是写给模型的 prompt，直接决定它**会不会用**、**会不会用对**。

| 写法 | 例子 | 问题 |
|---|---|---|
| ❌ 太简略 | "Calculator." | 模型不知道什么时候该用它，也不知道表达式怎么写 |
| ❌ 只说做什么 | "Evaluates math expressions." | 没说"每次计算都用"，模型觉得简单的算式自己就能算 |
| ✅ 说清何时用、怎么写、不要写什么 | "Use this tool for every calculation ... Do not use thousands separators, currency signs, percent signs" | 把模型常犯的格式错误提前堵住 |

参数描述里的例子（`"(5829 - 5735) / 5735 * 100"`）特别有用：模型会照着例子的格式写。

### 3.3 参数校验与错误回传

模型传来的参数，在执行前依次过三关（`Tool.run`）：

1. `json.loads`：是不是合法的 JSON？
2. 是不是一个对象（而不是列表、数字）？
3. pydantic 校验：参数齐不齐、类型对不对、有没有多余的参数？

**任何一关失败，都不抛异常，而是把错误变成一条文字回传给模型**，例如：

```
Error: invalid arguments: expression: Field required; expr: Extra inputs are not permitted.
```

为什么？工具出错时，让整个程序崩溃是最差的选择。模型看到错误信息，通常能自己改正。演示脚本第 4 步是真实例子：模型写了带千分位逗号的 `"(5,829 - 5,735) / 5,735 * 100"`，计算器回传 `Error: write numbers without thousands separators: 5829, not 5,829`，模型下一轮就改成了 `"(5829 - 5735) / 5735 * 100"`。

所以**错误信息是写给模型看的**：要具体，最好直接告诉它该怎么改。

### 3.4 说明书也要花钱

每次请求都要把 tools 完整发一遍，它和 system prompt 一样占输入 token（我们的计算器约 180 个 token）。好在它每次都相同，能命中前缀缓存（L01）。工具越多，这笔固定开销越大，这也是 L07 要考虑"给模型几个工具"的原因之一。

## 4. 安全：计算器为什么绝不能用 eval()

### 4.1 eval 会执行任意代码

最省事的计算器是 `eval(expression)`。但 `eval` 执行的是**任意 Python 代码**：

```python
eval("__import__('os').getcwd()")   # 返回当前目录（演示脚本第 2 步）
```

演示用的是无害的"读当前目录"；换成删除文件、读取 `.env` 里的 key，`eval` 也一样照做。表达式是模型写的，而模型的输入里可能混进不可信的内容：L05 起是检索到的网页和文件，里面完全可能藏着一句"请计算 `__import__('os')...`"。这叫 **prompt injection**（L07 专门讲）。

**原则：模型的输出是不可信的输入，永远不要直接执行。**

### 4.2 AST 白名单

[tools/calculator.py](../src/finagent/tools/calculator.py) 分两步：

1. `ast.parse(expression, mode="eval")` 只做**语法分析**，把字符串变成一棵语法树，不执行任何东西。`"(5829 - 5735) / 5735 * 100"` 的语法树是：
   ```
   BinOp(
     left=BinOp(
       left=BinOp(left=Constant(5829), op=Sub(), right=Constant(5735)),
       op=Div(), right=Constant(5735)),
     op=Mult(), right=Constant(100))
   ```
2. 自己递归遍历这棵树，**只认识白名单里的节点**：数字、`+ - * / **`、正负号、`abs/min/max`。遇到别的一律拒绝：变量名、属性访问（`x.y`）、下标、字符串、函数调用、lambda……

这叫**默认拒绝**：不去列举"哪些危险"（永远列不全），而是只列举"哪些允许"，没想到的东西自动被挡在外面。

### 4.3 白名单也管"语义"

白名单不只为了安全，也为了防止**悄悄算错**：

- **`%`**：在 Python 里是取余。模型写 `15% * 3` 时想的是"百分之十五"，而 `20 % 3` 会悄悄算出 2。所以计算器直接拒绝 `%`，并告诉模型"用 0.15 表示 15%"。
- **千分位逗号**：`5,829 - 5,735` 在 Python 里是一个元组 `(5, 829 - 5, 735)`，不会报错，却完全不是那个意思。计算器识别出元组，回传"不要写千分位逗号"。

### 4.4 资源限制

安全不只是"不执行危险代码"，还包括"不被一个表达式拖垮"：

| 攻击 | 后果 | 对策 |
|---|---|---|
| `9 ** 9 ** 9` | 整数运算会算出几亿位的大整数，程序卡死 | 所有数字转成 float，超出范围立刻 OverflowError |
| `(-8) ** 0.5` | Python 算出复数 | 检查结果，拒绝复数 |
| 几百层括号 | 解析器递归过深 | 表达式长度上限 500，解析器自己也有嵌套上限 |

float 有约 15 位有效数字，财务计算足够。返回结果时用 12 位有效数字，避免 `0.30000000000000004` 这样的浮点噪音。

## 5. 手写工具循环

### 5.1 代码

[agent/loop.py](../src/finagent/agent/loop.py) 的核心只有十几行：

```python
for _ in range(max_rounds):
    resp = client.chat(messages, json_mode=json_mode, tools=tools)
    responses.append(resp)
    messages.append(resp.to_message())        # ① 模型的回复（含调用请求）放回历史
    if not resp.tool_calls:                   # ② 不再调用工具：这就是最终回答
        return Generation(final=resp, ...)
    for call in resp.tool_calls:              # ③ 逐个执行（并行调用也在这里）
        step = registry.execute(call)         #    出错时 step.result 是 "Error: ..."
        messages.append({"role": "tool", "tool_call_id": call.id, "content": step.result})
# ④ 轮数用完还在调用：不再发请求，如实返回"没有最终答案"
```

对照 §2.3 的四个要点，每一行都能找到对应。

### 5.2 为什么必须有轮数上限

模型可能一直调用下去：反复验算、调用不存在的工具、陷入循环。没有上限，一道题就可能花掉无限的钱。我们设 `max_rounds=6`（FinQA 最多 5 步计算，而且可以并行）。达到上限时，这次尝试算失败，从头再试一次（不带之前的工具历史）。L07 会系统地讲终止条件、死循环检测和成本上限。

### 5.3 和结构化输出组合

L02、L03 的 `call_structured` 是"调用一次 → 校验 → 失败就带反馈重试"。有了工具，"一次生成"变成了"一整个工具循环"。所以把"生成"做成可以替换的参数 `generate`（[llm/structured.py](../src/finagent/llm/structured.py)）：

- 不带工具：`generate` 默认调用一次模型；
- 带工具：传入 `partial(run_tool_loop, client, registry=..., ...)`（[pipeline/answer.py](../src/finagent/pipeline/answer.py)）。

校验和重试的逻辑一行没改。重试时，之前的工具调用和结果都保留在历史里，不用重算。这就是**组合**：两个独立的机制，通过一个简单的接口拼在一起。

`StructuredResult` 也因此区分了两个数：`attempts`（尝试了几次）和 `len(responses)`（调用了几次模型）。L03 以前两者相等，现在一次尝试里可能有好几次调用。

### 5.4 实测发现：JSON mode 会让模型不愿意调用工具

最初的设计是：工具循环里每一轮都开 JSON mode（L02 的第一道防线）。冒烟测试时发现，带了工具，模型却**一次都没调用**。于是做了一个小实验（FinQA dev 里 8 道多步计算题）：

| 设置 | 调用了工具的题 |
|---|---|
| 开 JSON mode，system prompt 不提工具 | 0 / 8 |
| 开 JSON mode，system prompt 要求用工具 | 2 / 8 |
| 关 JSON mode，system prompt 不提工具 | 1 / 8 |
| 关 JSON mode，system prompt 要求用工具 | 6 / 8 |

两个结论，§7.4 在整个 dev 上验证了它们：

1. **只在工具描述里写"每次计算都用我"不够**，system prompt 里要明确要求。
2. **JSON mode 会压制工具调用。** 一种可能的解释：JSON mode 让模型强烈倾向于"直接输出一个 JSON 对象"，而调用工具要先输出另一种格式。我们看不到 DeepSeek 的内部实现，只能说这是实测到的现象。

所以最终的设计：**工具循环里不开 JSON mode**（`ToolsConfig.json_mode` 默认为 false），JSON 格式靠 prompt 要求 + pydantic 校验 + 带反馈的重试把关。L02 的三道防线少了第一道，但后两道仍在。实测结果也支持这个选择：v0.4 在 120 道题上平均尝试 1.02 次，几乎没有格式问题。

## 6. 新的评测集：FinQA

### 6.1 为什么用 FinQA

FinQA（Chen 等，2021，MIT 许可）的每道题都附带一页 10-K 财报：表格前的文字、一张表格、表格后的文字，外加一个标准答案程序（如 `subtract(5829, 5735), divide(#0, 5735)`）。它正好满足本课的需要：数字都给了，答错主要是读错、理解错或算错。标准答案程序在 L10 还有大用：可以直接转成"调用计算器"的训练数据。

我们把一页财报拼成一段纯文本上下文（中位数约 3900 个字符，也就是 1000 个 token 左右），放进 user 消息里。新的 prompt [answer_ctx_v1](../prompts/answer_ctx_v1.yaml) 要求"只用片段里的数字"。

### 6.2 清洗：两份标准答案互相核对

FinQA 每道题的标准答案有两份：`answer`（人写的文字，如 `"1.6%"`）和 `exe_ans`（程序算出的数，如 `0.01641`）。[parse_finqa_gold](../src/finagent/eval/datasets.py) 只保留**两份对得上**的题：

| answer | exe_ans | 结果 |
|---|---|---|
| `"1.6%"` | 0.01641 | 对得上（×100）→ 保留，标准答案 1.641%，小数位 1 |
| `"24.69%"` | 24.69136 | 对得上（程序里已经 ×100）→ 保留 |
| `"3.4%"` | -0.0339 | 符号对不上 → 丢掉 |
| `"25%"` | 0.19495 | 数值对不上 → 丢掉 |
| `"yes"` | "yes" | 不是数值题 → 丢掉 |

原始的 dev + test 共 2030 题，丢掉了 175 道对不上的（8.6%）、58 道非数值题、14 道同一页上一字不差的重复题。

数值用 `exe_ans`（更精确），小数位数用 `answer` 的写法（它决定容差，沿用 L03 的规则）。

**这个检查能发现什么、发现不了什么**：它能发现"文字和程序不一致"这类抄写错误；但如果程序本身就写错了，文字是照着程序抄的，两份照样一致。§7.6 就找到了好几道这样的题。

### 6.3 划分与分层

- 我们的 dev 只从 FinQA 的 dev.json 抽，test 只从 test.json 抽；FinQA 的 train.json 留给 L10 做训练数据。三者互不重叠，训练时就不会碰到评测题。
- **按计算步数分层**：1 步、2 步、3 步及以上，每层抽同样多的题（dev 各 40，test 各 50）。原始数据里 1 步的题占六成，按比例抽的话，多步题太少，看不出"计算器对多步计算帮助更大"这类差别。代价是：整体准确率不代表 FinQA 的原始分布，报告时要说明。

### 6.4 单位与符号

- **单位**：FinQA 的表格有的以千为单位，有的以百万为单位，标准答案就用表格的单位。所以 prompt 要求"单位跟着片段走，不做换算"，unit 只用 `percent` 或 `other`。
- **符号**：新增了 `sign_error` 错误类型（数值对、符号反了）。但题目问"下降了多少"时，答 42（下降 42）和 -42（变化 -42）都是对的。所以题目里有 decrease、decline、lower 这类方向词时，`sign_agnostic` 为 true，判分时不看符号。

### 6.5 不改动旧评测集

`EvalItem` 新增了 `context` 和 `sign_agnostic` 两个字段。如果直接把它们写进所有文件，FinanceBench 和种子题的文件内容就变了，L03 记录里的 `dataset_sha256` 全部对不上，新旧结果就没法比较。所以 `dump_items` 在这两个字段取默认值时不写出，旧文件逐字节不变（有测试保证）。**改评测代码时，要确保旧的"尺子"不受影响。**

## 7. 实验结果

本课所有实验共花费约 $0.25。

### 7.1 实验一：纯算术探针

[scripts/l04_arith_probe.py](../scripts/l04_arith_probe.py)：题目里直接给出所有数字，**只考算术**。答错只可能是算错，结果很干净。5 类题各 10 道，数字随机生成。

| 题型 | 心算 | 计算器 | 心算 + thinking |
|---|---|---|---|
| pct4：两个 4 位数的增长率 | 10/10 | 10/10 | 10/10 |
| pct7：两个 7 位数的增长率 | 10/10 | 10/10 | 10/10 |
| product：5 位数 × 4 位数，精确到个位 | 10/10 | 10/10 | 10/10 |
| cagr：5 年复合增长率（开 5 次方） | **6/10** | 10/10 | 10/10 |
| multi：(A + B + C) / (D − E)，6 位数 | 9/10 | 10/10 | 10/10 |
| **合计** | **45/50** | **50/50** | **50/50** |
| 花费 | $0.0036 | $0.0083 | $0.0345 |

（`runs/l04_arith/20260927-122534`）

读法：

1. **flash 的四则运算比预想的好得多**，连 7 位数的增长率、5 位数乘 4 位数都全对（它在 reasoning 里写了中间步骤，相当于用了草稿纸）。
2. 错误集中在**开方**（CAGR），而且错得"很像对的"：答错时的相对误差中位数只有万分之五。
3. 计算器和 thinking 都能补上，但计算器便宜约 4 倍。计算器组 50 题里有 48 题调用了工具，平均每题调用模型 2.36 次。

### 7.2 实验二：FinQA dev，不带工具 vs 带工具

控制变量：同一个模型（flash，关闭 thinking）、同样 120 道题、同样的上下文。

| | 不带工具（v0.4-notool） | 带工具（v0.4） |
|---|---|---|
| prompt | answer_ctx_v1 | answer_ctx_tools_v1（多一段"用计算器"的说明） |
| 准确率 | 68.3%（60.0 ~ 76.7） | **75.8%**（67.5 ~ 83.3） |
| 答错率 | 27.5% | 21.7% |
| 用了工具的题 | — | 86% |
| 每题花费 | $0.00025 | $0.00033 |
| 每题延迟 | 1.2s | 2.0s |
| 每题调用模型 | 1.02 次 | 1.92 次 |

配对比较：准确率 **+7.5 个百分点**，95% 区间 +1.7 ~ +13.3，McNemar p = 0.022 → **差异显著**。

按步数：1 步 70% → 75%，2 步 77.5% → 85%，3 步及以上 57.5% → 67.5%。

### 7.3 重复一次：显著性可能只是运气

L03 发现，温度 1.0 时同一系统跑两次，很多题的判分会变。所以两组各重跑了一次：

| | 第 1 次 | 第 2 次 | 两次平均 |
|---|---|---|---|
| 不带工具 | 68.3% | 69.2% | 68.8% |
| 带工具 | 75.8% | 72.5% | 74.2% |
| 差（配对） | +7.5（p = 0.022，显著） | +3.3（区间 −1.7 ~ +8.3，p = 0.34，**不显著**） | **+5.4（区间 +2.1 ~ +8.8）** |

同一个系统两次运行之间，不带工具组有 14 道题判分不同，带工具组有 11 道。

**怎么下结论**：

- 如果只跑了第一次，我们会报告"+7.5 个百分点，显著"；如果只跑了第二次，会报告"不显著"。**单次实验的结论，本身就带着运气。**
- 两次平均后（每道题的得分是两次的平均，再做配对 bootstrap），差异 +5.4 个百分点，区间不包含 0。更稳妥的结论是：**计算器确实有帮助，幅度在 +2 到 +9 个百分点之间，大约 +5。**
- 第一次的 +7.5 更可能是"真实效果 + 一点好运"。这种现象叫**赢家的诅咒**（winner's curse）：被选出来报告的那个结果，往往高估了真实效果。

以后遇到"刚好显著"的结果，先重复一次再下结论。重复还很便宜：第二次运行命中了大量前缀缓存，花费只有第一次的 55%~65%。

### 7.4 消融：模型不调用，工具就没用

| 设置 | 用了工具的题 | 准确率 |
|---|---|---|
| 带工具 + 说明 + 关 JSON mode（v0.4） | 86% | 75.8% |
| 带工具，**不给说明**（`--prompt answer_ctx_v1`） | 28% | 69.2% |
| 带工具 + 说明，**开 JSON mode**（v0.4-jsonmode） | 9% | 69.2% |
| 不带工具 | 0% | 68.3% |

§5.4 在 8 道题上的发现，在 120 道题上成立：不给说明、或者开着 JSON mode，模型基本不用工具，准确率就和不带工具时一样。**"给了工具"不等于"用了工具"**，工具使用率是必须监控的指标，报告里的"用了工具的题"就是为此加的。

### 7.5 工具到底帮了什么

直觉上，计算器帮的是"算得更准"。但数据不支持这个解释：

- 不带工具的两次运行里，一共有 66 个答错的数值答案，其中和标准答案相差**不到 5%** 的（"算得不太准"）只有 **4 个**；其余 62 个都差得很远，是取错了数或理解错了题。
- 实验一也说明 flash 的四则运算很准。

那 +5 个百分点从哪来？逐题看改善的 14 道题，主要是**把计算做完整**：

| 题目 | 不带工具 | 带工具 |
|---|---|---|
| RSU 授予的价值是多少？ | 两次都只给了授予数量 1,583,616 | 两次里有一次调用 `1583616 * 9.32`，得到 14,759,301 |
| 未来五年到期的长期债务合计？ | 一次对、一次只给了最后一年的 1,631,181 | 两次都调用 `204079 + 766451 + 822690 + 768588 + 1631181` |
| 2014 年 connected fitness 的营业利润率？ | 两次都说"缺少收入数据"，拒答 | 两次都在文字里找到了 1,920 万美元的收入，调用 `-13064 / 19200 * 100` |

system prompt 要求"每一步计算都用计算器"之后，模型的做题过程变了：先列出公式，再一步步算完。它不再跳步、不再半路停下，也更少直接照抄表格里的某个数。**工具改变的是模型的工作流程，而不只是计算精度。**这个发现只有逐题看才能得到，只看总分是看不出来的。

### 7.6 剩下的错误

带工具组两次都答错的 26 道题，大致分三类：

1. **取错数、理解错题**（最多）：比如该用 2014 年的数，用了 2015 年的；"增加了多少"答成了差值，标准答案要的是百分比。
2. **题意本身有歧义**：比如"从最高到最低的变化百分比"，以最高值还是最低值为基数都说得通。
3. **标准答案是错的**：程序写错了，而文字是照着程序抄的，所以 §6.2 的一致性检查发现不了。核对原文后，至少有 4 道：

| 题目 | FinQA 的标准答案 | 实际应该是 | 模型的回答 |
|---|---|---|---|
| ETR：2001 到 2002 年营业收入变化百分比（原文："增加了 4.11 亿，达到 12 亿"） | 192%（算成了 (1200 − 411) / 411） | 411 / 789 = 52.1% | 52.09% ✔ |
| IPG：10 月比 11 月多花了百分之多少 | 1229%（算的是两者之比） | 比值减 1 = 1129% | 1129.09% ✔ |
| ALXN：未来五年最低租金的年均值 | 4441（跳过了 2008 年，却把"之后年份"算进去） | 2008~2012 年的平均 3441.4 | 3441.4 ✔ |
| GS：某资产占其他资产的百分比 | 3.464（把两个十亿单位的数相减） | 16.77 / 20.234 = 82.9% | 82.88% ✔ |

也就是说，dev 上至少 3% 的题，模型"答对了却被判错"。这是所有公开评测集的通病，也是为什么**不要迷信排行榜上的小数点**。修正标注是作业 1。

### 7.7 结论

1. 计算器在 FinQA 上带来约 **+5 个百分点**（两次平均，区间 +2 ~ +9），代价是每题多约 0.9 次模型调用、花费高约 40%、延迟多约 0.8 秒。
2. 提升主要来自"把计算做完整"，而不是"算得更准"；flash 的四则运算本来就好，真正的算术弱点是开方类运算。
3. 工具要**被用上**才有效：system prompt 要明确要求，工具循环里不能开 JSON mode。
4. 单次实验的显著性不可靠，要重复验证。
5. 剩下的错误主要是读错、理解错，以及标准答案本身的错误。这些计算器帮不上，要靠更好的 prompt、检索（L05、L06）和 agent（L07）。

**v0.4 的选择**：带计算器（`configs/systems/v0.4.yaml`）。按规则，FinQA 的 test 留到 v0.7 里程碑再跑。

## 12. 参考答案

**1.** 函数由我们的代码执行。模型只输出一段"调用意图"：函数名和一段 JSON 格式的参数文本，放在回复的 `tool_calls` 里，`finish_reason` 是 `"tool_calls"`。

**2.** 因为模型只会生成文本，参数就是它生成的一段 JSON 文本，服务端不保证它合法。所以我们必须自己 `json.loads`，再用 pydantic 校验类型和必填项；任何一步失败都要当作正常情况处理。

**3.** 先追加模型的这条回复（assistant 消息，带着两个 tool_calls），再追加两条 `role: "tool"` 的消息，每条带上对应的 `tool_call_id` 和执行结果。`tool_call_id` 用来把结果和请求对上号，模型才知道哪个结果属于哪个算式。

**4.** 出错是正常情况（模型写错格式、传错参数），不应该让整个程序崩溃。把错误信息回传，模型通常能自己改正（演示脚本第 4 步：看到"不要写千分位逗号"之后，它去掉逗号重试了）。所以错误信息要写给模型看：具体，并且说明该怎么改。

**5.** `eval` 会执行任意 Python 代码，而表达式是模型写的，模型的输入可能被注入恶意内容。"默认拒绝"是只列出允许的东西（数字、四则运算、括号、几个函数），其余全部拒绝，而不是去列举哪些危险（永远列不全）。

**6.** `%` 在 Python 里是取余，模型写 `15%` 时想的却是百分之十五，`20 % 3` 会悄悄算出 2，不会报错。转成 float 是为了防止整数的 `**` 算出几亿位的大整数把程序卡死；float 超出范围会立刻抛出 OverflowError。

**7.** 模型可能反复调用、陷入循环，没有上限就可能无限花钱。达到上限时不再发请求，这次尝试算失败，`call_structured` 从头再试一次（不带之前的工具历史）。

**8.** 按 DeepSeek 文档，带 tools 的请求要把之前各轮的 `reasoning_content` 完整传回，否则会返回 400。我们实测去掉它时 flash 没有报错。仍然按文档做，是因为服务端随时可能开始严格检查，而且去掉思考过程后模型接不上自己的思路。

**9.** 实测开着 JSON mode 时，模型几乎不调用工具（120 道题里只有 9% 用了，关掉后是 86%）。关掉之后，JSON 格式靠 system prompt 的格式要求 + pydantic 校验 + 带反馈的重试来保证，实测平均只需要尝试 1.02 次。

**10.** 能发现"文字答案和程序结果不一致"的抄写类错误（比如符号反了、数值对不上）。发现不了"程序本身就写错了"的错误：文字是照着程序抄的，两份照样一致，比如 ETR 那道题，两份都是 192%。

**11.** 单次实验的结果带着运气（温度 1.0 下，同一系统两次运行有十几道题判分不同）。应该把两次合起来看：两次平均的差是 +5.4 个百分点，区间 +2.1 ~ +8.8，不包含 0，所以效果是真的，但幅度大约是 +5，不是 +7.5。第一次的 +7.5 有赢家诅咒的成分。

**12.** 主要来自"把计算做完整"：模型被要求每一步都用计算器之后，会先列公式再算完，不再跳步或照抄表格里的某个数。证据是逐题错误分析：不带工具时的 66 个错误答案里，只有 4 个是"数值接近、算得不准"；改善的 14 道题里，典型情况是不带工具时根本没做乘法、没把几个数加完，或者直接拒答。

**13.** 每次请求都要把完整的说明书发给模型，占输入 token（虽然能命中缓存）。工具越多，固定开销越大；而且说明书越长、工具越相似，模型越难选对该用哪个工具。

## 13. 下一课预告 · L05 RAG ① 基础管线

本课的 FinQA 实验有一个前提：**财报片段是直接给模型的**。现实中没人会帮你把正确的那一页找出来：一份 10-K 有 5 到 10 万个 token，整份塞进上下文又贵又慢，模型还容易漏掉中间的内容（lost in the middle）。

L05 要自己把相关的片段找出来：
- 下载 SEC 的 10-K 原文，切成小块（chunking），特别是表格怎么处理；
- 把每块变成向量（embedding），先用 numpy 手写暴力检索，再换成 FAISS；
- 回到 L03 的 FinanceBench：闭卷 37% 的基线，加上检索之后能到多少？还能用它自带的证据页码，直接测"检索有没有找对"（Recall@k）。

v0.4 的"阅读器 + 计算器"会原样接到检索后面：检索负责"找到数"，阅读器负责"读对数"，计算器负责"算对数"。
