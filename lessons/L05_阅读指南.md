## 第零轮 · 环境

### [ ] 第 0 步：安装与建索引（讲义 §10）
```powershell
pip install torch --index-url https://download.pytorch.org/whl/cu128
pip install -e ".[rag]"
python scripts/check_env.py --lesson 5
finagent build-corpus
finagent build-index
```
- **易错点**
  - 先装 CUDA 版 torch，再装 `.[rag]`。反过来的话，sentence-transformers 会从 PyPI 拉一个 CPU 版的 torch。
  - `check_env.py` 的 GPU 一栏要显示你的显卡；显示"CPU 版"就重装 torch。
  - `data/` 和向量模型缓存都不进 git。换一台电脑时，用这两条命令重新生成即可：这就是"大文件不进 git，但要能复现"（ADR-8）。

## 第一轮 · 原理

### [ ] 第 1 步：先运行演示脚本（20 分钟，不花钱）
```powershell
python walkthroughs/L05_retrieval.py
```
- **看什么**
  - 第 1 步：相似度矩阵里，哪一行对了、哪一行错了？对照脚本打印的"读法"，理解语义匹配的长处和表格行的麻烦。
  - 第 2 步：向量就是 384 个数，长度为 1。
  - 第 3 步：加不加查询前缀，在 50 道真实题目上差多少。
  - 第 4 步：暴力检索和 ANN 的速度、重合度。
  - 第 5 步：证据页上的块分别排第几？写着答案数字的那一块排第几？
- **易错点**：演示里的相似度数值换一台机器可能有细微差别，看排名和规律，不要背数字。

### [ ] 第 2 步：讲义 §1–§2　为什么要 RAG，数据从哪来（30 分钟）
- **知识点**
  - 闭卷的问题（编造）和 L04 的启发（给对页就能答对）
  - 为什么不把整份财报塞进 prompt：成本、延迟、lost in the middle、根本放不下
  - RAG 的六个步骤，离线和在线的分工
  - 为什么用 PDF 而不是 HTML（页码 → 自动评测检索）
  - 页码约定：怎么核对的
  - PDF 表格：按坐标重建行
- **易错点**
  - 猜外部数据的约定（页码从几开始），不去核对。弄错一页，Recall@k 就全错了，而且不会报错。
  - 以为 PDF 里有"表格"。其实只有带坐标的字。

### [ ] 第 3 步：讲义 §3　切块（30 分钟）
- **知识点**
  - 为什么切：长度上限（会悄悄截断）、一块一个主题、交给模型的内容要精
  - token 按向量模型的分词器来数（7 个词可能是 19 个 token）
  - 按行累加 + 重叠：把讲义里 A B C D 的例子在纸上推一遍
  - 不跨页的三个理由
  - 块首加标题
- **易错点**
  - 按字符数或词数切，结果大量块超过 512 个 token 被截断，而你完全不知道。`build-index` 会报告被截断的块数，要看一眼。
  - 重叠设得比块还大（配置校验会拦下）。
  - 块里只有正文，没有"是哪家公司、哪一年"。

### [ ] 第 4 步：讲义 §4　向量与检索（40 分钟）
- **知识点**
  - 向量模型怎么学出来的：对比学习（InfoNCE）
  - bi-encoder vs cross-encoder
  - 归一化后点积 = 余弦相似度
  - 查询前缀：训练时怎么用，推理时就怎么用
  - 相似度只看排名，不能用固定阈值
  - 暴力检索、FAISS、ANN（IVF、HNSW）的直觉和取舍
- **易错点**
  - 忘了归一化，点积就不再是余弦相似度，长的文本会占便宜。
  - 问题和段落都加了查询前缀，或者都没加。
  - 数据量不大时就上 ANN：多了近似误差，却没换来需要的速度。

### [ ] 第 5 步：讲义 §5–§6　检索评测与生成（35 分钟）
- **知识点**
  - Recall@k、文档命中、MRR；为什么 Recall@k 偏保守
  - 消融：标题（显著）、表格重建（对检索不显著）
  - 没命中的四类原因
  - 上下文格式：编号 + 出处；prompt 要求核对出处、用编号引用
  - small-to-big
- **易错点**
  - 只看端到端准确率，不单独评检索：答错了不知道是没找到还是没读对。
  - 在 test 上调检索参数。检索评测免费，更容易忍不住多看，纪律同样适用。
  - 以为"对检索没用"就是"没用"：表格重建的价值可能在阅读。

## 第二轮 · 代码（按数据流动的顺序）

```
data/ingest.py        PDF → 每页的文字（rows_text 重建表格行）
      ↓
rag/chunker.py        每页 → 若干块（按行累加、重叠、不跨页、标题）
      ↓
rag/embedder.py       块 → 向量（bge-small，归一化）
      ↓
rag/index.py          向量 → 索引（numpy 暴力 / FAISS）
      ↓
rag/retriever.py      build_index（离线）；Retriever.search、ContextBuilder（在线）
      ↓
eval/run.py           prepare_sources → format_context → pipeline/answer.py（L04 的阅读器 + 计算器）
```

### [ ] ① [src/finagent/data/ingest.py](../src/finagent/data/ingest.py)（20 分钟）
- **知识点**：`doc_title` 的正则；`download_pdf` 先写 `.part` 再改名（下载中断不会留下半个文件）；`clean_text` 为什么保留换行；`rows_text` 的中线平均；`Layout` 两种抽取方式；`build_corpus` 同时写页文件和文档信息。
- **易错点**：`rows_text` 的 `tolerance` 太小，同一行被拆开；太大，相邻两行被合并。3 磅是看了实际输出后选的。

### [ ] ② [src/finagent/rag/chunker.py](../src/finagent/rag/chunker.py) ★（25 分钟）
- **知识点**：`TokenCounter` 是批量接口；`chunk_page` 的累加和重叠逻辑；"带上重叠就装不下这一行"时放弃重叠；`_split_long` 的递归对半拆；`Chunk.embed_text` 的标题开关。
- **怎么读**：对照 `tests/test_rag.py` 的 `test_chunk_packing_and_overlap`，它就是讲义里 A B C D 的例子，用 `fake_counter` 把每行的 token 数写在行尾。
- **易错点**：在循环里修改正在遍历的列表；重叠部分和新行加起来超过上限。

### [ ] ③ [src/finagent/rag/embedder.py](../src/finagent/rag/embedder.py)（10 分钟）
- **知识点**：`model` 属性延迟加载（`import torch` 要好几秒）；`device="auto"`；`normalize_embeddings=True`；`embed_queries` 加前缀、`embed_passages` 不加；`count_tokens` 不含特殊 token；`revision` 固定模型版本。

### [ ] ④ [src/finagent/rag/index.py](../src/finagent/rag/index.py)（15 分钟）
- **知识点**：`argpartition` + 只对前 k 个排序；`take_along_axis`；FAISS 的 `index_factory` 与 `METRIC_INNER_PRODUCT`；IVF 要先 `train`；FAISS 结果不足 k 个时用 −1 占位。
- **易错点**：`np.argsort` 对全部 4 万个分数排序也能用，只是慢。先想清楚"只要前 k 个"。

### [ ] ⑤ [src/finagent/rag/retriever.py](../src/finagent/rag/retriever.py) ★（25 分钟）
- **知识点**
  - `build_index`：切块 → 向量化 → 统计截断 → 写 `vectors.npy`、`chunks.jsonl`、`meta.json`
  - `Retriever.load` 会核对"索引是用现在这份配置建的吗"，不一致就报错
  - `search_many` 批量检索
  - `Source` 和 `header()`：页码显示时 +1
  - `ContextBuilder` 的三种模式；`_expand_to_pages` 去重并保持排名顺序
- **易错点**：改了 `configs/index/*.yaml` 却没重建索引。`Retriever.load` 专门拦这种情况：宁可报错，也不要让结果悄悄对不上。

### [ ] ⑥ [src/finagent/config.py](../src/finagent/config.py) 的 `RetrievalConfig`、`IndexConfig`（10 分钟）
- **知识点**：系统配置（怎么用检索）和索引配置（索引怎么建）分开；`oracle` 模式不需要 index（校验器）；`ChunkConfig` 校验重叠小于块大小。

### [ ] ⑦ [src/finagent/eval/retrieval.py](../src/finagent/eval/retrieval.py) + [scripts/l05_retrieval_eval.py](../scripts/l05_retrieval_eval.py)（15 分钟）
- **知识点**：`first_hit_rank`、`recall_at`、`mrr`；为什么一次取前 20、再算不同 k 的 Recall；`--show-misses` 做错误分析。

### [ ] ⑧ [src/finagent/eval/run.py](../src/finagent/eval/run.py) 的改动（15 分钟）
- **知识点**
  - `prepare_sources`：并发答题**之前**一次性批量检索（更快，也避免多个线程同时用 GPU）
  - `check_prompt_fits` 多了检索的情况
  - `_retrieval_fields`：逐题记录检索结果、命中、引用；只认方括号里的编号
  - `retrieval_stats`：命中 / 没命中时的准确率
  - `TYPE_CHECKING`：不做检索的评测不必导入 numpy、torch
- **易错点**：`re.findall(r"\d+", "[2] 3M 10-K 2018")` 会把 2018 也当成引用编号，所以只认 `\[(\d+)\]`。

### [ ] ⑨ [src/finagent/cli.py](../src/finagent/cli.py) 的新命令（5 分钟）
- `build-corpus`、`build-index`、`search`；`ask` 遇到带检索的系统会先检索、打印材料出处。

### [ ] ⑩ 测试 [tests/test_rag.py](../tests/test_rag.py)（15 分钟）
- **知识点**：`BagOfWordsEmbedder`（词袋哈希的假向量模型，结果确定、不需要下载）；手写的 `CHUNKS` 和 `PAGES`；`test_title_helps_tell_companies_apart` 用两块几乎一样的正文说明标题的作用；FAISS Flat 和 numpy 结果逐一相同；`pytest.importorskip`。

## 最容易错的 10 件事（读完之后回来自查）

- [ ] 1. 先装了 `.[rag]` 再装 CUDA 版 torch，结果用的是 CPU 版。
- [ ] 2. 猜外部数据的约定（页码从 0 还是从 1 开始），不去核对。
- [ ] 3. 按字符或词数切块，大量块超过模型的长度上限被悄悄截断。
- [ ] 4. 块里没有公司和年份的信息，同一家公司不同年份的报告分不开。
- [ ] 5. 向量没有归一化，或者问题和段落的前缀用法和训练时不一致。
- [ ] 6. 用固定的相似度阈值判断"相关"。
- [ ] 7. 只看端到端准确率，不单独评测检索，也不做 oracle 实验，不知道瓶颈在哪。
- [ ] 8. 只把检索到的小块交给模型，表头和关键数字不在块里。
- [ ] 9. 改了索引配置却没重建索引（项目里会报错，自己写的系统可能不会）。
- [ ] 10. 50 道题上准确率高了 15 个百分点，就宣布"显著提升"。
