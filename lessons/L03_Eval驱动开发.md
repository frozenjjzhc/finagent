## 0. 这节课学完你能做到

1. 从零搭建一个评测集：选数据、固定版本、清洗标准答案、划分 dev / test。
2. 设计判分规则：数值容差怎么定、哪些交给规则、哪些交给 LLM 裁判。
3. 知道 LLM 裁判有哪些偏差，以及怎么用人工标注校准它。
4. 用 bootstrap 置信区间和配对检验判断一个差距是不是真的。
5. 让每一次评测都可复现，并且知道什么行为会让评测失效。

## 1. 为什么这一课最重要

L02 结束时，我们的处境是：v2 在 10 道题上答对 8 道，v3 答对 7 道，**说不准谁更好**。没有可靠的评测，后面的每一个改动（加工具、加检索、微调）都只能凭感觉判断好坏。

工业界把这叫 **eval-driven development（评测驱动开发）**：先定义"好"是什么、怎么量，再去改系统，每次改动都用同一把尺子量。面试里 "How would you evaluate an LLM system?" 几乎必问，这一课就是完整的答案。

## 2. 构建评测集

### 2.1 数据从哪来

| 候选 | 用不用 | 原因 |
|---|---|---|
| **FinanceBench** 开源子集（150 题） | ✅ 用 | 真实财报问题，有专家写的标准答案和证据页码；三种题型各 50 道 |
| 10 道种子题（L01 手工核实） | ✅ 用 | 已经对照 10-K 核实过 |
| FinQA | ⏳ 挪到 L04 | 它的题目必须配合给定的财报片段才能作答，而我们现在是闭卷系统；L04 正好要给模型提供上下文 |

FinanceBench 的三种题型：
- **metrics-generated**：数值计算题，比如"FY2018 资本开支是多少百万美元""FY2019 固定资产周转率是多少（保留两位小数）"；
- **domain-relevant**：领域判断题，比如"3M 是资本密集型企业吗"，答案是"是 / 否 + 理由"；
- **novel-generated**：开放分析题，比如"剔除并购影响后，哪个分部拖累了增长"。

### 2.2 数据治理：让评测集可以复现

评测集是项目的"规格"，它一变，分数就没法和以前比。我们做了五件事：

1. **固定版本**：下载地址固定到 FinanceBench 仓库的 commit `6e138b2`，而不是会变动的 main 分支；
2. **核对哈希**：下载后核对 sha256，文件被改过就拒绝继续；
3. **脚本生成**：`scripts/build_evalsets.py` 从原始数据生成 `evalsets/*.jsonl`，同样的输入永远得到同样的输出；
4. **提交到 git**：生成的评测集和 `MANIFEST.json`（来源、版本、哈希、各划分的题数）都提交，`tests/test_evalsets.py` 会检查文件没被手工改过；
5. **许可证与署名**：FinanceBench 是 **CC BY-NC 4.0**，允许非商业使用，但必须署名。署名写在 `evalsets/README.md`。

**一次真实的事故**：第一次生成的评测集文件用的是 Windows 换行符（`\r\n`）。Python 在 Windows 上以文本模式写文件时，会自动把 `\n` 换成 `\r\n`，于是同一份评测集在 Windows 和 Linux 上的哈希会不同。修复方法：写文件时指定 `newline="\n"`；计算哈希前统一换行；加 `.gitattributes` 让 git 对 `.jsonl` 始终使用 LF。

### 2.3 统一格式

所有评测集都转成同一种格式（`eval/datasets.py` 的 `EvalItem`），判分代码只需要认识一种格式。关键字段是 `answer_type`：

| answer_type | 判分方式 | 题数 |
|---|---|---|
| `number` | 程序按容差比较 | FinanceBench 50 + 种子 9 |
| `text` | LLM 裁判对照参考答案 | FinanceBench 100 |
| `invalid_premise` | 识破前提错误才算对（陷阱题） | 种子 1 |

### 2.4 清洗标准答案

FinanceBench 数值题的标准答案写法五花八门：`$1577.00`、`$8.70`、`24.26`、`1.9%`、`-0.02`。单位藏在题目里（"in USD millions"、"Answer in USD billions"、"ratio"……）。

**规则不是想出来的，是逐一看过 50 道题之后总结出来的**：

| 标准答案 | 题目里的提示 | 换算结果 |
|---|---|---|
| `1.9%`（以 % 结尾） | — | 1.9，percent |
| `$1577.00` | USD millions | 1577，USD_millions |
| `$8.70` | USD billions | 8700，USD_millions |
| `24.26`、`-0.02`、`93.86` | ratio / ROA / 天数 | 原值，other |
| `$5.00` | 没说单位 | **不猜**，返回 None，交给裁判 |

最后一行体现一个原则：**看不懂就交给人（或裁判），不要瞎猜。** 猜错的标准答案，比没有标准答案更糟。

### 2.5 划分 dev / test

- **dev（50 道）**：调 prompt、做对比实验时随便用；
- **test（100 道）**：只在里程碑时跑，**不能根据 test 的结果去改系统**，否则 test 就变成了 dev，分数不再代表真实水平；
- **分层划分**：每种题型各挑固定数量进 dev，保证 dev 和 test 的题型比例一致；
- **固定随机种子**：划分可复现；
- **种子题只放 dev**：它们在 L01、L02 里被用来挑 prompt，已经"用过了"。

## 3. 判分规则

### 3.1 能用规则判的，就不用模型判

规则判分便宜、可复现、没有偏差。所以判分顺序是（`metrics.py` 的 `grade_item`）：

```
输出没通过校验               → invalid（💥）
陷阱题                       → 识破前提 correct / 说不知道 abstained / 给了答案 incorrect
status = unknown             → abstained（🤷）
status = invalid_premise     → incorrect（错误地声称前提不成立）
数值题，且给了 value          → 按容差比较（规则）
其余（文字题，或数值题只给了文字）→ 交给 LLM 裁判
```

### 3.2 数值容差：三个来源取最大

```
允许的误差 = max( 相对误差 1% × |标准答案|,
                  标准答案末位的一半,
                  单题额外容差 )
```

- **相对误差 1%**：适合大数字。1577 允许 ±15.77。
- **标准答案的精度**：题目要求"保留两位小数"时，标准答案 0.01 代表 [0.005, 0.015)。如果只用相对误差，容差只有 0.0001，模型答 0.013 会被误判为错。
- **单题额外容差**：种子题 q06 的标准答案是 18.5%，但 Amazon 10-K 里写的是四舍五入后的 19%，两个都应该算对，所以单独给 ±0.5。

**换算会改变精度**：`$8.70` billion 的精度是 0.01 billion = 10 million。换算成百万美元后，小数位数从 2 变成 -1，末位的一半是 5 百万。`parse_gold_number` 专门处理了这一点。

### 3.3 比率与百分比、数量级错误

- **比率 ↔ 百分比**：ROA 的标准答案是 `0.01`（比率），模型答 `1.3%` 也应该算对。无量纲的数，单位标签常常标得不准，所以比较时原值、×100、÷100 都试一下。
- **数量级错误**：题目要 billions、模型按 millions 填了数（差 1000 倍），和数字本身算错是两种不同的问题。判分时给它们打上不同的**错误类型标签**（`scale_error` 和 `wrong_value`），报告里会统计各类错误的数量，这是 L06 **错误分析**的基础。

### 3.4 不能只看一个指标

| 指标 | 公式 | 说明 |
|---|---|---|
| 准确率 | 答对 / 全部 | 主指标；拒答也算"没答对" |
| 给出答案时的准确率 | 答对 / (答对 + 答错) | 模型"敢答"的时候有多可靠 |
| 拒答率 | 没答 / 全部 | 覆盖率的反面 |
| 答错率 | 答错 / 全部 | 很肯定地答错，对财报问答危害最大 |

只看准确率会掩盖一个重要区别：**一个系统可以靠多拒答来降低答错率，准确率却几乎不变。** 本课的实验就遇到了这种情况（第 7 节）。

## 4. LLM 当裁判

### 4.1 怎么判

FinanceBench 有 100 道文字题，只能用另一个大模型来判（`eval/judge.py` + `prompts/judge_v1.yaml`）：

- **参考答案制**：给裁判看题目、专家的参考答案和候选答案，只问"候选答案对不对"，**不让裁判用自己的知识重新答题**；
- **二分类**：只判 correct / incorrect，不打 1–10 分。分数制的尺度很难统一，二分类更稳定；
- **只看结论和关键数字**：缺少次要细节不算错，结论不同或关键数字错才算错；
- **输出同样是 JSON**，推理在前、判定在后，复用 L02 的"JSON mode → 校验 → 带反馈重试"。这套逻辑在本课被抽成了通用函数 `llm/structured.py` 的 `call_structured`。

### 4.2 裁判的偏差和对策

| 偏差 | 表现 | 我们的对策 |
|---|---|---|
| 位置偏差 | 比较两个答案时，偏向前面（或后面）的那个 | 我们只判一个答案，不做两两比较 |
| 长度偏差 | 偏向写得长的答案 | 只给裁判看最终回答，**不给推理过程**（`candidate_text`） |
| 自我偏好 | 偏向和自己风格相近的答案 | 裁判用 v4-pro，被测系统用 flash |
| 系统性误判 | 某类题总是判错 | 和人工标注对比，做**校准** |

### 4.3 校准：裁判能信几分

裁判给出的分数能不能信，要拿人工标注来对：`scripts/judge_agreement.py` 把裁判的判定导出成表格，你人工标注后计算两个指标：

- **一致率**：你和裁判结论相同的比例；
- **Cohen's kappa**：扣除"碰巧一致"之后的一致程度。1 表示完全一致，0 表示和瞎猜一样。

为什么要看 kappa：假设 90% 的答案都是错的，裁判不看内容、一律判"错"，一致率也有 90%，而 kappa 接近 0。

```
kappa = (实际一致率 - 碰巧一致率) / (1 - 碰巧一致率)
碰巧一致率 = Σ_类别 (裁判判为该类的比例 × 人工判为该类的比例)
```

作业 1 会让你标注 23 条裁判判定。

### 4.4 实测发现：裁判自己也会犯格式错误

分析调用记录发现：三次 dev 评测里裁判（v4-pro）一共被调用了 85 次，其中 **23 次输出没通过校验**，需要重试：22 次是把字段名 `reasoning` 写成了 `reason`，1 次是 JSON 后面多了内容。说明 judge_v1 的格式说明还不够明确。

**但这一轮我们没有改它。** 原因是本课的一个重要原则：**在一轮对比实验中，测量工具必须保持不变。** 三个 prompt 版本和 test 基线都是用 judge_v1 判的分，结果才能互相比较。重试之后判定仍然有效，代价是裁判费用多出约 37%（真正需要的是 62 次调用，实际用了 85 次，合计也只有几分钱）。改进裁判留给作业 3，改完之后需要重新校准，旧结果也不能再和新结果直接比较。

## 5. 统计：结论什么时候可信

### 5.1 题目越少，分数越"飘"

`walkthroughs/L03_statistics.py` 第 1 步模拟了一个**真实准确率 70%** 的系统，用不同数量的题反复去测：

| 题数 | 测出的分数（中间 95% 的范围） | 标准差 |
|---|---|---|
| 10 | 40% ~ 100% | 14.9 个百分点 |
| 50 | 58% ~ 82% | 6.4 |
| 150 | 62% ~ 77% | 3.8 |
| 1000 | 67% ~ 73% | 1.5 |

同一个系统只测 10 道题，分数可能在 40% 到 100% 之间乱跳。**题数翻 4 倍，波动大约减半**（波动和 1/√n 成正比）。

### 5.2 bootstrap 置信区间

现实中我们只有一次评测结果，没法重复出题。bootstrap 的思路是：**把手上这批题当作"总体"，从中有放回地重抽**。

```
1. 从 n 道题的结果里，有放回地抽 n 个（有的题会被抽到多次，有的一次都没抽到）
2. 算这次抽样的准确率
3. 重复 2000 次，得到 2000 个准确率
4. 排序，取第 2.5% 和第 97.5% 位置的值，就是 95% 置信区间
```

它回答的问题是："换一批同样难度的题，准确率大概会落在什么范围？" 我们的 test 基线是 37%，区间 27% ~ 47%：**这 100 道题只能把真实水平定位到 ±10 个百分点左右**。

### 5.3 比较两个系统：一定要配对

两个系统各算各的区间再看是否重叠，这种做法太保守。更好的做法是**配对**：两个系统答的是同一批题，逐题比较。

- **配对 bootstrap**：每次重抽的是题目，两个系统在同一批抽到的题上比，算差值的区间。题目本身的难易被抵消了，灵敏得多。**区间不包含 0**，差异才可能是真的。
- **McNemar 检验**：只看"两个系统结果不同"的题。A 对 B 错有 a 道，A 错 B 对有 b 道。如果两个系统其实一样好，这些题应该像抛硬币一样一半一半。p 值就是"纯靠运气出现这么不平衡（或更不平衡）"的概率。

```
p = 2 × P(二项分布 Bin(a+b, 0.5) ≤ min(a, b))
```

我们的判定标准（`finagent compare`）：**两种方法都说显著，才算显著；一个说是、一个说否，标为"边缘"**。

用它重新分析 L02：v2 − v3 的配对差是 +10 个百分点，区间 +0 ~ +30，McNemar p = 1.00。**L02 的数据确实不足以说明 v2 更好。**

### 5.4 需要多少道题

准确率约 70% 时，想让单个系统的 95% 置信区间缩到 ±5 个百分点：

```
n ≈ (1.96 / 0.05)² × 0.7 × 0.3 ≈ 323 道题
```

我们的 dev 只有 50 道，只能发现十几个百分点以上的差距。**这不是缺点，而是事实**：置信区间诚实地告诉你这个评测集能分辨到什么程度。

## 6. 可复现

### 6.1 每次评测一个不可变的记录目录

`runs/eval/<时间>_<系统>_<prompt>_<评测集>-<划分>/`：

| 文件 | 内容 |
|---|---|
| `results.jsonl` | 每道题：题目、标准答案、系统回答、判分、错误类型、花费 |
| `summary.json` | 汇总指标、置信区间、按题型拆分、错误类型、成本、延迟 |
| `report.md` | 给人看的报告 |
| `config.yaml` / `prompt.yaml` / `eval.yaml` | 系统配置、prompt 文件、评测设置的快照 |
| `meta.json` | git commit、有没有未提交的修改、评测集哈希、日期参数、依赖版本 |

目录已存在就报错（`mkdir(exist_ok=False)`），**绝不覆盖旧记录**。

### 6.2 一次真实的事故：先提交，再跑评测

第一次跑 test 基线后，`meta.json` 显示 `dirty: True`：L03 的代码当时还没提交。**这次评测对应的代码，以后没人能准确还原。** 处理方式：
1. 把第一次的结果作废；
2. 提交代码（commit `2369180`）；
3. **事先声明**"干净的那一次就是正式结果，不管分数更高还是更低"，再重新跑；
4. 正式结果：37.0%，`dirty: False`。

第 3 步很关键：如果两次都跑，再挑分数好看的那个报告，就是**挑樱桃**（cherry-picking），和对 test 调参一样会让评测失去意义。

### 6.3 日期参数

prompt 里有"今天的日期"，它会影响模型的回答（L01 的发现）。所以 `finagent eval --today 2026-09-27` 把日期固定下来并记录在 `meta.json` 里，复现旧结果时传同样的日期。

## 7. 实验结果

### 7.1 先验证评测工具本身

在 10 道种子题上跑 v0.2（prompt v2），结果应该和 L02 手工核对的一致：

- 结果是 7 对 1 错 2 没答，L02 是 8 对 0 错 2 没答；
- 查报告发现，差别来自 q09：模型这次答了 **$72,477M**，接近 10-K 里"汽车销售"那个子项（72,480），而 L02 那次答对了。**判分规则没问题，是模型的回答变了。**

先用已知答案验证工具，再用工具去测未知，这是任何测量都要做的第一步。

### 7.2 dev 上比较三个 prompt（50 题，judge_v1）

| prompt | 准确率（95% 区间） | ✅ 对 | ❌ 错 | 🤷 没答 | 给出答案时的准确率 | 花费 |
|---|---|---|---|---|---|---|
| v1 | 32%（20% ~ 46%） | 16 | 24 | 9 | 40% | $0.022 |
| v2 | 36%（24% ~ 50%） | 18 | 23 | 9 | 44% | $0.014 |
| v3 | 30%（18% ~ 44%） | 15 | 15 | 20 | 50% | $0.010 |

配对比较（`finagent compare`）：

| 比较 | 指标 | 差值（95% 区间） | McNemar p | 结论 |
|---|---|---|---|---|
| v2 − v1 | 准确率 | +4（-6 ~ +16） | 0.73 | 不显著 |
| v2 − v3 | 准确率 | +6（-6 ~ +20） | 0.55 | 不显著 |
| v2 − v3 | 答错率 | +16（+2 ~ +30） | 0.057 | **边缘** |

按题型拆开：数值计算题三个版本**都只有 18%**，它需要某一年报表里的具体数字，闭卷做不了，是**知识**问题，prompt 解决不了（要靠 L04 的工具和 L05 的检索）。

### 7.3 为什么选 v3

1. 三个版本的准确率**没有显著差异**；
2. v3 **少答错 16 个百分点**（边缘显著）：它把很多"编一个答案"变成了"说不知道"；
3. PRD 的用户故事 U4 要求"没有把握就说不知道，而不是编"。

换个角度：如果用"答对 +1 分、答错 -1 分"来打分，v1 得 -8、v2 得 -5、v3 得 0。**选用哪个指标，本身就是一个产品决策**：它取决于答错的代价有多大。

这也**推翻了 L02 基于 10 道题暂定 v2 的决定**。小样本的结论靠不住，这里是一个活生生的例子。

### 7.4 test 基线，以及随机性有多大

v0.3（answer_v3）在 test（100 题）上：**准确率 37.0%**（27% ~ 47%），给出答案时的准确率 49%，拒答 25%，答错 38%，每题花费约 $0.0002（含裁判），P50 延迟 1.3 秒。这是 SCOREBOARD 的**第一行 test 基线**，之后每个里程碑都和它比。

作废的那一次和正式这一次，是同一个系统在同一批题上跑两次，比较结果：

- 总准确率 34% 对 37%，差 3 个百分点，**不显著**；
- 但有 **35 道题**两次的判分不一样。

**单道题层面的随机性非常大，只是正负相互抵消了。** 根源是采样温度：我们从没设置过 temperature，DeepSeek 默认是 1.0，每次生成都带随机性。作业 2 会研究这个问题。

## 12. 参考答案

**1.** FinQA 的题目要配合给定的财报片段才能作答，而 v0.3 是闭卷系统。放进来测的不是系统能力，而是题目缺条件。它留到 L04，那时我们会把片段提供给模型。

**2.** 评测集是衡量系统的尺子，尺子一变，前后分数就没法比较。固定版本和哈希保证每次用的是同一份数据；脚本生成加提交到 git，保证任何人都能得到同样的文件，也能看出它有没有被改过。

**3.** 算对。0.01 保留两位小数，代表 [0.005, 0.015)，0.013 在范围内。规则取"相对误差 1%"和"标准答案末位的一半（0.005）"中较大的那个作为容差，所以判为正确。

**4.** 准确率把"答错"和"不答"一视同仁。比如 v2 和 v3 的准确率差不多，但 v3 少答错 16 个百分点：它把很多编造变成了拒答。对财报问答，这个区别非常重要，只看准确率就看不到。

**5.** 位置偏差：我们只判单个答案，不做两两比较。长度偏差：不给裁判看推理过程。自我偏好：裁判用和被测系统不同的模型。系统性误判：用人工标注来校准。

**6.** 一致率会被类别比例误导：如果大多数答案都是错的，裁判一律判错也能有很高的一致率。kappa 扣除了"碰巧一致"的部分，反映的是真实的判断能力。

**7.** 从 n 道题的结果中有放回地抽 n 个，算一次准确率；重复 2000 次，取第 2.5% 和第 97.5% 位置的值。它回答"换一批同样难度的题，准确率大概会在什么范围内波动"。

**8.** 两个系统答的是同一批题，逐题比较可以抵消题目本身难易的影响，比各算各的区间灵敏得多。McNemar 只看两个系统结果不同的题；两边都对或都错的题不提供区分信息。

**9.** 一轮对比实验中，测量工具必须保持不变。三个 prompt 和 test 基线都用 judge_v1 判分，结果才能互相比较；重试后判定仍然有效，只是多花一点钱。改进裁判要单独做，并重新校准。

**10.** 代码没提交，以后就没法准确还原这次评测用的代码，结果不可复现。如果已经先跑了：把那次结果作废，提交代码，**事先声明**用干净的那一次作为正式结果，再重跑。不能两次都跑完再挑分数高的，那是挑樱桃。

**11.** 单道题层面的随机性很大（温度 1.0 下的采样），只是在总数上正负相互抵消了。所以：单次运行的逐题结论不可靠；比较两个系统时，一部分差异只是随机性造成的；需要置信区间，或者降低温度、多跑几次取平均。
