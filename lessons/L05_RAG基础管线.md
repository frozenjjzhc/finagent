## 1. 为什么需要 RAG

### 1.1 前几课留下的两个事实

- **L03（闭卷）**：模型不知道很多具体数字，FinanceBench dev 上只有 30% 的准确率，而且 46% 的题是**很肯定地答错**（编的）。
- **L04（给定上下文）**：只要把正确的那一页交给模型，它就能读对、算对。

那能不能每个问题都把正确的那一页交给模型？现实中没人帮你找。本课要让系统**自己找**：这就是 RAG（Retrieval-Augmented Generation，检索增强生成）。

### 1.2 为什么不把整份财报塞进 prompt

| 做法 | 每题输入多少 token | 问题 |
|---|---|---|
| 整份 3M 2018 10-K（160 页） | 约 12 万 | 贵（每题约 $0.036，是 RAG 的 20 倍左右）、慢；模型容易漏掉长文中间的内容（lost in the middle） |
| 84 份财报全部 | 约 835 万 | 任何模型都放不下；而且得先知道问的是哪一份 |
| **RAG：只放最相关的 5 页** | 约 5000 | 便宜、快；但要能找对 |

（token 数用 bge 的分词器统计，DeepSeek 的分词器数出来会有些差别，数量级相同。）

### 1.3 RAG 的完整流程

```
离线（建一次，几分钟）                         在线（每个问题都要做）
  ingest   PDF → 每页的文字                      retrieve  问题 → 向量 → 最相似的 5 个块
  chunk    每页 → 若干小块（带标题）               generate  这些块所在的页 → prompt → 模型回答
  embed    每个块 → 一个向量
  index    存起来，支持"找最相似的 k 个"
```

对应的代码：`data/ingest.py` → `rag/chunker.py` → `rag/embedder.py` → `rag/index.py` → `rag/retriever.py` → 复用 L04 的 `pipeline/answer.py`（阅读器 + 计算器）。

**关键洞察**：L04 做好的"阅读器 + 计算器"原样接在检索后面，prompt 里的 `{{context}}` 从"FinQA 给的那一页"换成"检索到的几页"。这就是为什么 L04 先做阅读器。

## 2. 数据：从 PDF 到每页的文字

### 2.1 为什么用 FinanceBench 自带的 PDF

FinanceBench 的每道题都标注了**证据在哪份文档的第几页**。用同一批 PDF、同样的页码，就能**自动**判断检索有没有找到正确的那一页，不需要人工看，也不需要调用模型。

原计划是从 SEC EDGAR 下载 HTML 版本的 10-K，但 HTML 没有页码，就没法和证据页对照。所以语料用 FinanceBench 仓库里的 PDF（固定到和评测集同一个 commit）。

**语料范围**：评测集用到的 84 份文档（dev 和 test 都包括），共 12013 页。test 题目用到的文档也在库里：语料是"图书馆"，不是"答案"。它们对 dev 题目来说还是干扰项，比如同一家公司不同年份的报告。

### 2.2 页码从 0 开始还是从 1 开始？核对一下

FinanceBench 的 `evidence_page_num` 是从 0 还是从 1 数的？文档没写。如果弄错一页，Recall@k 就全错了，而且不会报错。

核对方法：FinanceBench 还给了每个证据页的**原文**。把我们抽出的第 p−1、p、p+1 页分别和原文比较词的重合度。结果 189 个证据页**全部**在"第 p 页"匹配得最好，所以页码从 0 开始，和 PyMuPDF 的页序一致。给人和模型看的时候，统一显示 p+1，也就是 PDF 阅读器里看到的页码。

**教训**：外部数据的约定（页码从几开始、单位、时区），不要猜，找办法核对。

### 2.3 表格：PDF 里没有"表格"，只有带坐标的字

PDF 只记录"在 (x, y) 位置画一个字"。PyMuPDF 默认按文本块输出，而财务报表里每个单元格都是一个块，抽出来是这样的：

```
Depreciation and amortization
1,488
1,544
1,474
```

模型看不出 1,544 属于哪一年。[data/ingest.py](../src/finagent/data/ingest.py) 的 `rows_text` 换了一种做法：纵坐标相差不超过 3 磅的字算作同一行，再按横坐标从左到右排：

```
(Millions) 2018 2017 2016
Depreciation and amortization 1,488 1,544 1,474
```

3M 现金流量表那一页从 355 行变成了 46 行，表头的年份和每一行的数字对齐了。局限：双栏排版会把左右两栏拼在一起；一个单元格折成两行时会被拆开。

两种抽取方式都保留了（`financebench_pages.rows.jsonl` 和 `.text.jsonl`），§5.3 用评测来比较它们。

### 2.4 其他细节

- 12013 页中有 65 页抽不出文字（扫描版，是图片）。要读它们得做 OCR；好在没有一个证据页落在其中（已核对）。
- PDF 库用的是 PyMuPDF：快（84 份 PDF 抽取约 30 秒），效果好；它是 AGPL 许可，开源的学习项目可以用，闭源商用要注意。

## 3. 切块

### 3.1 为什么要切

1. **向量模型有长度上限**：bge-small 最多读 512 个 token，超过的部分会被**悄悄截掉**，不报错。
2. **一块最好只讲一件事**：一整页往往讲好几件事，压成一个向量，每件事都被"平均"掉了，检索时反而不容易命中。
3. **交给模型的内容要精**：越多越贵，也越容易干扰模型。

本课默认每块**最多 256 个 token，相邻两块重叠 32 个 token**。块多大最好，L06 会扫一遍。

### 3.2 token 按向量模型自己的分词器来数

同样长度的文字，token 数可能差很多：

```
"Depreciation and amortization 1,488 1,544 1,474"    7 个词 → 19 个 token
```

数字被切得很碎（"1,488" 被切成好几个 token）。财报满是数字，如果按词数估计，块会比预想的长很多，超过 512 就被截断。所以 `chunk_page` 的计数函数是可以替换的：建索引时传入向量模型分词器的计数（`Embedder.count_tokens`），测试时用简单的数词。

### 3.3 按行累加，带重叠

[rag/chunker.py](../src/finagent/rag/chunker.py) 一行一行往块里装，装不下了就开新块，新块开头重复上一块末尾的几行。例子（最多 6 个 token、重叠 2 个，括号里是每行的 token 数）：

```
行：A(3) B(2) C(2) D(4)
块 1：A B      再装 C 就是 7 > 6，开新块
块 2：B C      新块先带上块 1 末尾不超过 2 个 token 的行（B），再装 C
块 3：C D      同理带上 C，再装 D，正好 6
```

- **为什么按行**：经过 §2.3 的处理，一行往往就是表格的一行。按行切，不会把"Depreciation and amortization"和它的数字切到两块里。
- **为什么重叠**：落在两块交界处的内容，至少完整地出现在其中一块里。
- 超长的一行（极少数没有换行的大段文字）会先按词对半拆，拆到不超长为止。

### 3.4 不跨页

每块只来自一页，所以每块都有确定的页码：
- 才能和 FinanceBench 的证据页比较（Recall@k）；
- 引用时才能说清"第几页"；
- §6.2 的"扩展成整页"才能做。

块的 id 形如 `3M_2018_10K:p59:c1`（文档名 + 页码 + 这一页的第几块）。

### 3.5 块首加文档标题

一块文字"Net sales increased 5%"，看不出是哪家公司、哪一年的。84 份文档里同一家公司常有好几年的报告（Adobe 有 2015、2016、2017、2022 四份）。所以每块送去向量化之前，开头加上文档标题，比如 `3M 10-K 2018`。

这个小改动效果很大，§5.3 的消融实验：**R@5 从 30% 提高到 48%**。

### 3.6 结果

84 份文档 → **41766 个块**，平均 224 个 token，没有一个超过 512。在 RTX 4070 笔记本 GPU 上，切块加向量化约 2.5 分钟。

## 4. 向量与检索

### 4.1 向量（embedding）是什么

向量模型把一段文字变成一串数（bge-small 是 384 个数），**意思相近的文字，向量也相近**。

它是怎么学会的？用大量"问题 → 相关段落"的配对做**对比学习**：同一批训练数据里，让每个问题的向量靠近它的正确段落，远离同一批里的其他段落（这种损失叫 InfoNCE）。学完之后，"How much was returned to shareholders?"和"The Company paid dividends..."的向量就会靠得很近。

我们用的是 **bi-encoder（双塔）**：问题和段落**分别**过同一个模型，各得一个向量，再算相似度。好处是段落的向量可以提前算好存起来，查询时只需算问题这一个向量。（L06 的 reranker 是 cross-encoder：把问题和段落拼在一起过模型，更准，但不能提前算，只能用来给少量候选重新排序。）

### 4.2 余弦相似度

两个向量越接近，余弦相似度越大（最大为 1）。向量都先缩放到长度为 1（归一化），这时**点积就等于余弦相似度**，找最相似的块就是做一次矩阵乘法：

```
scores = 问题向量 @ 所有块的向量.T      # (1, 384) × (384, 41766) → 41766 个相似度
取最大的 5 个
```

### 4.3 查询前缀

bge 训练时，问题前面都加了一句 `Represent this sentence for searching relevant passages: `，段落前面不加。用的时候也要照做。

在 dev 的 50 道真实题目上比较（演示脚本第 3 步）：加前缀 R@5 = 48%、R@10 = 54%；不加前缀 R@5 = 42%、R@10 = 58%。**两者互有高低，50 道题上看不出显著差别。** 我们仍然按模型的训练方式加前缀：这是模型作者的要求，不应该根据 50 道题上几个百分点的波动去改。

### 4.4 相似度的两个特点（演示脚本第 1 步的真实结果）

演示用 4 个问题和 5 个文本块（4 个普通句子、1 行表格）算了相似度矩阵：

1. **语义匹配**：问"What was R&D spending?"，和"Research, development and related expenses were $1.8 billion"一个词都不重合，向量模型仍然把它排第一。关键词检索做不到这一点。
2. **但它也会错**：
   - 问"资本开支"，排第一的是"研发费用"那一句：两者都是"花了多少钱"，小模型分不清相近的概念。
   - 问"销售增长多快"，排第一的竟是一行满是数字的表格。表格行几乎没有能理解的文字，它的向量和什么问题都"有点像"。
3. **所有相似度都挤在 0.42 ~ 0.70 之间**：绝对值没有意义，只看排名。不能用"相似度 > 0.7 才算相关"这种固定阈值。

### 4.5 暴力检索、FAISS 与 ANN

[rag/index.py](../src/finagent/rag/index.py) 有两种实现，接口相同：

- **NumpyIndex**：手写的暴力检索。问题和**每一个**块都算一次相似度，用 `argpartition` 挑出前 k 个再排序。
- **FaissIndex**：FAISS 库。`Flat` 和暴力检索完全一样（有测试保证结果逐一相同）；`HNSW32`、`IVF256,Flat` 是**近似检索（ANN）**。

演示脚本第 4 步的实测（41766 个块，50 个问题，每题取前 10；时间每次运行会有波动）：

| 索引 | 查 50 题 | 和精确结果的重合 |
|---|---|---|
| numpy 暴力检索 | 约 15ms | 100% |
| FAISS Flat（精确） | 约 32ms | 100% |
| FAISS HNSW32 | 约 0.7ms | 88% |
| FAISS IVF256（查 8 个簇） | 约 2.7ms | 87% |

ANN 的直觉：
- **IVF**：先用 k-means 把所有向量分成 256 簇，查询时只在离问题最近的 8 个簇里找。就像找书时先找到对的书架，而不是翻遍整个图书馆。
- **HNSW**：把向量连成一张多层的"邻居网络"，从上层的少数点出发，沿着邻居一路走向目标，像先坐飞机、再换火车、最后步行。

代价是可能漏掉一些真正最近的邻居（上表重合度 87%~88%）。**4 万个向量时，暴力检索每题不到 1 毫秒，完全够用**，所以项目默认用它。ANN 要到几百万、上亿个向量时才有必要。先手写暴力检索，才知道 FAISS 在帮你做什么（ADR-7）。

## 5. 检索评测：不调用大模型，不花钱

### 5.1 指标

[eval/retrieval.py](../src/finagent/eval/retrieval.py)：

| 指标 | 含义 |
|---|---|
| **Recall@k**（页命中） | 前 k 个块里至少有一个来自证据页的题目比例（有多个证据页时，找到任意一页就算） |
| 文档命中@k | 前 k 个块里至少有一个来自证据所在的文档：比页命中宽松，两者之差 = "找对了报告、没找对页" |
| **MRR** | 第一个命中的排名的倒数的平均：第 1 名命中得 1 分，第 3 名得 1/3，没命中得 0 |

例子：证据在 `3M_2018_10K` 第 59 页，检索结果依次是（3M_2022_10K, 40）、（3M_2018_10K, 58）、（3M_2018_10K, 59）→ Recall@1 = 0，Recall@3 = 1，文档命中@2 = 1，这道题的 MRR 得分 = 1/3。

### 5.2 结果（dev 50 题，`python scripts/l05_retrieval_eval.py`）

| R@1 | R@3 | **R@5** | R@10 | R@20 | 文档命中@5 | MRR |
|---|---|---|---|---|---|---|
| 16% | 42% | **48%**（95% 区间 34% ~ 62%） | 54% | 68% | **92%** | 0.308 |

**读法**：92% 的题能找到正确的报告，但只有 48% 找到正确的页。检索的主要问题是"找对了报告、找错了页"。

### 5.3 消融：标题和表格处理

这两个实验只需要重建索引、重跑检索评测，不花一分钱：

| 索引 | 改动 | R@5 | 和默认比（配对） |
|---|---|---|---|
| fb_bge_small（默认） | — | 48% | — |
| fb_bge_small_notitle | 块首不加文档标题 | 30% | 默认高 **18 个百分点**（区间 +8 ~ +30，McNemar p = 0.012），**显著** |
| fb_bge_small_text | 不按行重建表格 | 46% | +2（区间 −4 ~ +8，p = 1.00），不显著；R@10 反而是 text 高 8 个百分点（p = 0.125，边缘） |

- **标题**：没有标题时，同一家公司不同年份的报告几乎无法区分，文档命中@5 也从 92% 掉到 84%。
- **按行重建表格**：对**检索**没有显著帮助。它的价值可能在**阅读**（模型读表时能对上年份），要用生成实验来验证（作业 2）。一个改动在一个环节没用，不代表在另一个环节也没用。

### 5.4 没找到的题，都是什么原因

用 `--show-misses` 列出 top-5 没命中的 26 道题，逐题看，大致几类：

| 原因 | 例子 |
|---|---|
| **年份混淆** | 问 Corning FY2022 的营运资本，前 5 名里有 Corning 2020、2021 年的报告 |
| **问题很抽象，需要的是报表** | "Does Corning have positive working capital?"需要资产负债表那一页，但问题里的词和一堆数字的表格对不上 |
| **证据在别的文档类型里** | 问 Ulta Beauty 的 SG&A 变化，证据在季度业绩新闻稿里，检索却去了别家公司的 10-K |
| **需要好几页** | dev 里有 12 道题要用 2~3 页证据（比如存货周转率要利润表的销货成本 + 资产负债表的存货）；**没有一道题把所有证据页都找全**，只有 2 道找到了其中一页 |

这些正是 L06（BM25、按公司和年份过滤、重排）和 L07（agent 分几次检索）要解决的问题。

## 6. 生成：把检索结果交给模型

### 6.1 上下文长什么样

[rag/retriever.py](../src/finagent/rag/retriever.py) 的 `format_context` 把每段材料编号，标明出处：

```
[1] Netflix 10-K 2017, page 45
Table of Contents NETFLIX, INC. CONSOLIDATED BALANCE SHEETS (in thousands, ...)
...

[2] Netflix 10-K 2017, page 13
...
```

prompt [answer_rag_v1](../prompts/answer_rag_v1.yaml) 相对闭卷的 answer_v3 改了三处：
1. 只用给定的材料，材料里没有就说不知道；
2. **材料是搜索引擎找来的，可能来自别的公司、别的年份，用之前先核对出处**；
3. `sources` 写材料的编号（如 `["[2]"]`），这样引用可以自动核对。

计算器那一段和 L04 一样保留。

### 6.2 small-to-big：用小块检索，用整页回答

演示脚本第 5 步的真实例子（dev 的 fb07661），问 Block（原 Square）FY2020 经营活动产生的现金流，证据是 BLOCK_2020_10K 的现金流量表（第 89 页，从 0 数）。这一页被切成 5 块，它们的排名：

```
c0  排第 2      开头是 "SQUARE, INC. ... Cash flows from operating activities:"   ← 进了前 5，但没有答案
c2  排第 152    开头就是 "Net cash provided by operating activities 381,603 ..."   ← 答案在这里
c1  排第 468    最后一行也是这一行（重叠）
c3、c4 更靠后
```

**写着答案的那一行所在的块，排在第 152 名以外。** 问题问的是"cash flow from operating activities"，和表头那块的措辞最像；而满是数字的表格行，向量模型很难排上去（§4.4）。

- 只把前 5 个块交给模型（v0.5-chunk）：模型回答"材料里没有经营活动现金流净额这一行"，拒答。
- `ContextBuilder` 的 `context: page` 模式：只要一页里**任何一块**进了前 5，就把**整页**交给模型（同一页只给一次）。c0 排第 2，所以整个第 89 页都给了模型，它读到 381,603（千美元），换算成 381.6 百万美元，答对。

这叫 **small-to-big**（也叫 parent document retrieval）：用小块检索，用整页回答。§7.4 用实验验证了它。

反过来也有不需要 small-to-big 的时候：Netflix 流动负债那道题，排第 1 的块最后一行就是 `Total current liabilities 5,466,312`（切块时的重叠还让这一行在下一块开头又出现了一次），只给块也能答对。

### 6.3 引用

模型在 `sources` 里写编号，评测时解析方括号里的数字（`"10-K 2018"` 里的数字不算），再检查引用的材料里有没有证据页。v0.5 引用了证据页的比例是 51%，和检索命中率（48%）差不多：证据给到了，模型基本都能找到并引用它。

## 7. 实验结果

四组系统，同一个模型（flash，关闭 thinking），FinanceBench dev 50 题，裁判不变（judge_v1）。闭卷和 v0.5 各跑两次（L04 的教训）。本课所有实验共花费约 $0.12。

### 7.1 总表

| 系统 | 给模型什么 | 准确率（95% 区间） | 答错 | 拒答 | 每次调用的输入 token |
|---|---|---|---|---|---|
| v0.3（闭卷） | 什么都不给 | 30% / 30%（18 ~ 44） | 46% / 42% | 24% / 28% | 约 1200 |
| **v0.5（检索 + 整页）** | 检索到的 5 块所在的页 | **44% / 46%**（30 ~ 60） | **14% / 12%** | 42% / 42% | 约 4900 |
| v0.5-chunk（检索 + 只给块） | 检索到的 5 个块 | 28%（16 ~ 42） | 20% | 52% | 约 2300 |
| v0.5-oracle（直接给证据页） | 标注的证据页 | **88%**（78 ~ 96） | 10% | 2% | 约 2000 |

（"/"前后是两次运行。）

### 7.2 RAG 的主要作用：不再瞎编

配对比较 v0.5 和闭卷：

| 指标 | 第 1 次 | 第 2 次 | 结论 |
|---|---|---|---|
| 准确率 | +14 个百分点（区间 −4 ~ +32，p = 0.21） | +16（区间 −2 ~ +34，p = 0.15） | **不显著**：两次平均 +15，区间 −2 ~ +32，碰到了 0 |
| 答错率 | **−32**（区间 −48 ~ −14，p = 0.002） | **−30**（区间 −44 ~ −16，p = 0.001） | **显著，而且两次都显著** |

**怎么理解**：
- RAG 最确定的效果是**答错大幅减少**：闭卷时模型靠记忆编了很多数字；有了检索，找不到证据时它会说"材料里没有"。拒答从 24% 升到 42%，就是这些"原本会编的题"。
- 准确率大约提高 15 个百分点，但 **50 道题不足以证明它**。这是 L03 讲过的样本量问题：50 道题时，一个准确率的 95% 区间宽达 ±14 个百分点左右（表中 30% ~ 58%），两个系统的差距要大过这种波动才显著。等 test（100 题）在 v0.7 里程碑上跑，或者扩大 dev。
- 闭卷时 5 次 `false_invalid_premise`（错误地声称前提不成立）在 v0.5 中一次都没有出现：有材料可查，模型不再凭记忆判断"这家公司没有这个业务"。

**意外发现：RAG 让结果更稳定。** 同一个系统跑两次，闭卷有 15 道题判分不同，v0.5 只有 **1 道**。答案来自给定的材料，而不是随机的"回忆"，温度带来的波动就小得多。

### 7.3 错误分解：瓶颈在检索

`summary.json` 里的检索统计（第 1 次运行）：

| | 题数 | 准确率 |
|---|---|---|
| 证据页被检索到 | 24 | **79%**（第 2 次运行 83%） |
| 证据页没被检索到 | 26 | **12%**（19 道拒答、4 道答错、3 道答对） |

再对照 oracle（直接给证据页）的 **88%**：
- **阅读的上限**：证据给到了，阅读器能答对 88%。
- **检索的损失**：v0.5 比 oracle 低 44 个百分点（区间 +30 ~ +58，显著），主要原因是一半的题没找到证据页。

这就是 L06 的方向：**先提升检索**。阅读器已经不错，再改 prompt 的收益有限。这种"先把错误分成两桶、再决定优化哪边"的方法，就是 L06 要系统讲的错误分析。

没命中却答对的 3 道题也值得看：比如 Nike 那道题，模型引用的是同一份 10-K 的另一页，那一页也有需要的数字。FinanceBench 只标了一个证据页，所以"没命中"不一定真的没找到。Recall@k 是一个**偏保守**的指标。

### 7.4 small-to-big 有用

只给 5 个块（v0.5-chunk）的准确率是 28%，扩展成整页（v0.5）是 44%：**+16 个百分点（区间 +6 ~ +26，p = 0.008），显著**。两者的检索结果完全相同（R@5 都是 48%），差别全在"交给模型什么"。

- 证据页被检索到时，只给块的准确率只有 50%，整页是 79%：块里常常缺表头（哪一列是哪一年）或者缺那一行数字（§6.2 的 Block 例子）。
- 代价：输入 token 从约 2300 增加到约 4900，第一次运行的花费约是只给块的 2 倍。

### 7.5 按题型

| 题型 | 闭卷（两次） | v0.5（两次） | oracle |
|---|---|---|---|
| novel-generated（新闻稿、10-Q 里的具体事实） | 25% / 31% | **62% / 69%** | 88% |
| domain-relevant（需要判断的财务问题） | 35% / 41% | 41% / 41% | 82% |
| metrics-generated（按公式计算的指标） | 29% / 18% | 29% / 29% | 94% |

计算题（metrics-generated）在 oracle 下高达 94%，v0.5 却没有进步：这类题要的是利润表、资产负债表这种满是数字的页，恰好是向量检索最弱的地方（§4.4），而且常常需要两页（§5.4）。

### 7.6 剩下的问题（逐题看）

- **证据只找到一半**：Kraft Heinz 的存货周转率要用利润表（第 49 页，销货成本）和资产负债表（第 51 页，存货）。检索只找到了第 51 页，模型回答"材料里没有销货成本，没法算"。它没有编，这是正确的行为，但题没答上。
- **题目和系统规则冲突**：3M 的固定资产净值，题目要求"Answer in USD billions"，而 system prompt 规定金额用百万美元。模型回答 8.738，单位却标成了百万美元，被判为数量级错误（v0.5 和 oracle 都这样）。**用户的要求和系统的规则冲突时，要在 prompt 里写清楚谁优先。**
- oracle 下还有 6 道没答对，多数是题意或标准答案本身有歧义，比如 AMEX 那道题的标准答案是"不用营业利润率衡量"，模型却照样算了一个营业利润率。

### 7.7 成本和延迟

| | 闭卷 | v0.5 第 1 次 | v0.5 第 2 次 |
|---|---|---|---|
| 50 题系统花费 | $0.0055 | $0.038 | $0.009 |
| 输入的缓存命中率 | 86% | 33% | **96%** |
| 延迟 P50 | 1.3s | 1.6s | 1.5s |

RAG 每题的输入是闭卷的 4 倍，第一次运行花费约是闭卷的 7 倍。第二次运行几乎全部命中缓存（同样的问题检索到同样的页，prompt 前缀完全相同），花费降到约四分之一。线上系统如果有大量重复的问题，缓存会让 RAG 便宜很多。

### 7.8 结论

1. RAG 最确定的效果是**大幅减少编造**（答错率从 44% 左右降到 13% 左右，两次都显著）；准确率约提高 15 个百分点，但 50 道题上不显著。
2. **瓶颈是检索**：证据页只找到一半；找到时准确率约 80%，直接给证据页时 88%。
3. **small-to-big**（用块检索、给整页）显著好于只给块。
4. **块首加标题**让检索的 R@5 从 30% 提高到 48%，免费且显著。
5. 检索结果让回答更稳定：两次运行只有 1 道题判分不同（闭卷是 15 道）。

**v0.5 的选择**：`configs/systems/v0.5.yaml`（检索 top-5 块 → 整页 + 计算器）。FinanceBench 的 test 按规则留到 v0.7 里程碑。

| 方法 | 适合 | 不适合 | 本项目 |

## 13. 参考答案

**1.** ingest（PDF → 每页文字）、chunk（切块）、embed（向量化）、index（建索引）是离线的，建一次反复用；retrieve（检索）和 generate（把检索结果交给模型回答）是每个问题都要做的。

**2.** 一份 10-K 约 12 万 token：每题都付这么多输入的钱（约是 RAG 的 20 倍），延迟高，模型还容易漏掉长文中间的内容。而且 84 份文档合计约 835 万 token，根本放不下，还得先知道问的是哪一份。

**3.** FinanceBench 标注了证据所在的文档和页码。用同一批 PDF、同样的页码，就能自动判断检索有没有找到正确的页；HTML 没有页码，就做不到。

**4.** 从 0 开始。FinanceBench 给了每个证据页的原文，我们把抽出的第 p−1、p、p+1 页分别和原文比较，189 个证据页全部是第 p 页匹配得最好。

**5.** PDF 里没有表格结构，只有带坐标的字；默认按文本块输出时，每个单元格变成单独一行，看不出数字属于哪一年。`rows_text` 把纵坐标相近（±3 磅）的字归为同一行，再按横坐标排序，把表格的行拼回来。

**6.** 向量模型按它自己的 token 计长度，超过上限（512）就悄悄截断。同样的文字，数字多的 token 多得多（7 个词可能是 19 个 token），按词数估会低估长度。

**7.** 按行：一行往往是表格的一行，不会把行名和数字切开。重叠：落在交界处的内容至少完整地出现在一块里。不跨页：每块有确定的页码，才能和证据页比较、才能引用、才能扩展成整页。

**8.** 正文常常看不出是哪家公司、哪一年（"Net sales increased 5%"）。加上"3M 10-K 2018"这样的标题，问题里的公司名和年份就能匹配上。消融实验中 R@5 从 30% 提高到 48%，显著（p = 0.012）。

**9.** bi-encoder 把问题和段落分别编码成向量再比较，段落向量可以提前算好，适合从大量段落里快速检索。cross-encoder 把问题和段落拼在一起输入模型，更准但不能提前算，只适合给少量候选重新排序（L06 的 reranker）。

**10.** 归一化之后，点积就等于余弦相似度，检索只需一次矩阵乘法。0.65 算不算相关说不清：相似度的绝对值挤在一个很窄的范围里（演示中是 0.42 ~ 0.70），只有排名有意义，不能用固定阈值判断相关与否。

**11.** 暴力检索精确、简单，但要和每个向量比较，数据量大时慢。ANN（HNSW、IVF）快很多，但可能漏掉一些真正最近的邻居（本课实测和精确结果的重合度 87%~88%）。本项目只有 4 万个向量，暴力检索每题不到 1 毫秒，没必要用 ANN。

**12.** Recall@k：前 k 个结果里有没有证据页。文档命中：有没有找对报告（比页命中宽松）。MRR：第一个命中排得多靠前。说 Recall@k 偏保守，是因为标准答案只标了一个证据页，而同样的信息可能出现在别的页上（Nike 那道题"没命中"，却答对了）。

**13.** 用小块检索（匹配更准），但交给模型的是块所在的整页（信息更全：表头、同一张表的其他行都在）。实验中准确率从 28% 提高到 44%，显著。代价是输入 token 大约翻倍。

**14.** 准确率的提升幅度（约 15 个百分点）相对 50 道题的波动来说不够大，区间碰到了 0；答错率的下降幅度大得多（约 30 个百分点），而且方向非常一致（闭卷答错、RAG 不答错的题很多，反过来的很少），所以显著。另外，RAG 的主要作用本来就是把"编造"变成"不知道"，这首先体现在答错率上。

**15.** oracle 直接给证据页，相当于"检索永远正确"，它的准确率就是阅读器的上限。和真实检索的差距就是检索造成的损失。本课：oracle 88%，v0.5 44%~46%；证据被检索到时准确率约 80%，没检索到时约 12%。所以瓶颈在检索。

**16.** RAG：知识多、会更新、要出处。长上下文：文档少、需要通读全文。微调：教行为和格式（怎么用工具、怎么输出），不适合记会变的事实。一句话：事实用 RAG 查，能力用微调教。

## 14. 下一课预告 · L06 RAG ② 检索质量工程

L05 的错误分解说得很清楚：证据给到了，模型能答对约 80%；问题是一半的题**没找到证据页**。L06 专攻检索：

- **错误分析**：先把作业 1 的分类做完，看哪类错误最多；
- **BM25**：关键词检索，擅长向量检索不擅长的精确词（"Item 7A"、"inventory turnover"、具体年份）；
- **hybrid + RRF**：把两种检索的排名融合起来；
- **按公司、年份过滤**：解决年份混淆；
- **cross-encoder 重排**：先用快的方法找 50 个候选，再用准的方法排出前 5；
- **切块大小扫一遍**：128 / 256 / 512 个 token 哪个最好？

检索评测不花钱，所以 L06 可以放开做消融实验，每个组件都用 Recall@k 说话，最后再用端到端准确率确认。
