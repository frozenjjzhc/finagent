## 第一轮 · 原理

### [ ] 第 1 步：讲义 §1–§2　构建评测集（30 分钟）
- **知识点**
  - 数据选择：为什么用 FinanceBench，为什么 FinQA 推迟到 L04
  - 数据治理五件事：固定版本、核对哈希、脚本生成、提交到 git、许可证署名
  - 统一格式 `EvalItem`，`answer_type` 的三种取值
  - 标准答案清洗：规则来自逐题检查；看不懂就不猜
  - dev / test 划分：分层、固定种子、test 的使用纪律
- **怎么读**：打开 `evalsets/README.md` 和 `MANIFEST.json` 对照着看。
- **易错点**
  - 下载地址用 `main` 分支：数据哪天被上游更新了，你的分数就悄悄变了。
  - **根据 test 的结果改系统**：test 就变成了 dev，分数不再可信。这是本课最重要的纪律。
  - 把已经用来挑 prompt 的题放进 test（种子题只能放 dev）。
  - 标准答案看不懂时靠猜：猜错的标准答案比没有标准答案更糟。
  - Windows 上以文本模式写文件，换行会变成 `\r\n`，导致跨平台哈希不同。

### [ ] 第 2 步：讲义 §3　判分规则（30 分钟）
- **知识点**
  - 规则优先：能用规则判的，就不用模型
  - 五种判分结果：correct / incorrect / abstained / invalid / error
  - 容差 = max（相对 1%，标准答案末位的一半，单题容差）
  - 比率与百分比互换；数量级错误单独标记
  - 四个指标：准确率、给出答案时的准确率、拒答率、答错率
- **怎么读**：拿 `tests/test_metrics.py` 里 `test_grade_number` 的每一行，自己先判一遍再看答案。
- **易错点**
  - 只用相对误差：标准答案 0.01、模型答 0.013，会被误判为错。
  - **换算单位时忘了精度也要跟着变**：$8.70 billion → 8700 million，精度从 0.01 变成 10。
  - 把"答错"和"不答"混为一谈：它们对用户的伤害完全不同。
  - 只看准确率一个数。

### [ ] 第 3 步：讲义 §4　LLM 当裁判（25 分钟）
- **知识点**
  - 参考答案制、二分类、只看结论和关键数字
  - 四种偏差及对策（位置、长度、自我偏好、系统性误判）
  - 校准：一致率、Cohen's kappa
  - 测量工具在一轮对比中必须保持不变
- **怎么读**：对照 `prompts/judge_v1.yaml` 读 §4.1，每条规则对应哪个判分原则。
- **易错点**
  - 让裁判"自己重新答题"再比较：裁判的知识也会出错，而且那就不是在对照参考答案了。
  - 把推理过程也给裁判看：写得长的答案容易被判为对（长度偏差）。
  - **只看一致率**：类别不平衡时一致率会虚高，要看 kappa。
  - 人工标注时先看裁判的结论，被它带偏。
  - 一边比较、一边改裁判：前后的分数就没法比了。

### [ ] 第 4 步：先运行统计演示脚本，再读讲义 §5（35 分钟）
```powershell
python walkthroughs/L03_statistics.py
```
脚本的第 1–4 步分别对应：题数与波动、bootstrap、重新分析 L02、需要多少道题。
- **知识点**
  - 波动 ∝ 1/√n
  - bootstrap：有放回地重抽，取中间 95%
  - 配对 bootstrap 与 McNemar 检验
  - 显著 / 边缘 / 不显著的判定标准
  - 样本量估算：n ≈ (1.96 / 半宽)² × p(1−p)
- **易错点**
  - 两个系统各自的区间有重叠，就认为"一定没差异"：这种判断太保守，要用配对比较。
  - **把"不显著"理解成"两者一样好"**：不显著只是说"这批题不足以证明有差异"。
  - 把 p = 0.057 当成"完全没有差异"，或者把 p = 0.049 当成"铁证"：边界附近要如实说"边缘"。
  - bootstrap 不固定随机种子：同样的数据每次算出不同的区间。

### [ ] 第 5 步：讲义 §6–§7　可复现与实验结果（20 分钟）
- **知识点**
  - 记录目录里的 7 个文件各记录什么
  - 先提交代码，再跑里程碑评测
  - 不挑樱桃：事先声明哪一次是正式结果
  - 固定日期参数
  - 先用已知答案验证评测工具
- **易错点**
  - 在有未提交修改的代码上跑 test（`meta.json` 里的 `dirty: true`）。
  - 同一评测跑多次，只报告分数最好的那次。
  - 评测工具还没验证，就直接拿它下结论。

## 第二轮 · 代码（自底向上）

依赖关系（箭头表示"用到了"）：

```
cli.py (eval_cmd, compare)
   └──> eval/run.py ──> eval/judge.py ──> llm/structured.py ──> llm/base.py
             │                └──> eval/metrics.py ──> eval/datasets.py ──> schemas.py
             ├──> eval/metrics.py
             └──> pipeline/answer.py ──> llm/structured.py
scripts/build_evalsets.py ──> eval/datasets.py
scripts/judge_agreement.py
```

### [ ] ① [src/finagent/eval/datasets.py](../src/finagent/eval/datasets.py)（15 分钟）
- **知识点**：`EvalItem` 的字段；`model_validator` 保证数值题一定有标准答案；`parse_gold_number` 的正则和换算；`_digits_of` 处理精度变化。
- **易错点**
  - 正则里 `(?P<name>...)` 是命名分组，`m.group("num")` 按名字取值，比按序号取值更不容易出错。
  - 负数、千分位逗号、`%`、`$` 都要处理；有 `$` 却不知道单位时返回 `None`，而不是默认当成百万。

### [ ] ② [scripts/build_evalsets.py](../scripts/build_evalsets.py)（15 分钟）
- **知识点**：固定 commit 的下载地址；sha256 校验；分层抽样（`rng.sample`）；`MANIFEST.json`。
- **易错点**
  - 抽样前要先**排序**，否则划分结果会随原始文件的行序变化。
  - 写文件要指定 `newline="\n"`（换行事故）。

### [ ] ③ [src/finagent/eval/metrics.py](../src/finagent/eval/metrics.py) ★（25 分钟，最重要）
按顺序读：`allowed_error` → `grade_number` → `grade_item` → `summarize` → `bootstrap_ci` → `paired_bootstrap_diff` → `mcnemar_exact`。
- **知识点**
  - `@dataclass` 的 `Grade`：label、grader、detail、tag 四个字段
  - `JudgeFn` 类型别名：判分函数只依赖"一个能判分的函数"，而不是具体的裁判类，方便测试时替换
  - `random.Random(seed)`：独立的随机数生成器，不影响全局随机状态
  - `math.comb` 计算二项分布
- **易错点**
  - `grade_item` 里判断的**顺序**很重要：必须先处理陷阱题和拒答，再比较数值。
  - McNemar 的 p 值是**双侧**的（乘 2），并且不能超过 1。
  - bootstrap 取分位数时下标的边界，差一位就会错。

### [ ] ④ [src/finagent/llm/structured.py](../src/finagent/llm/structured.py)（10 分钟）
- **知识点**：`Generic[T]` 和 `TypeVar`：一份代码适用于任意 pydantic 模型；`result` 参数让调用方传入子类实例（`AnswerResult`）。
- **易错点**：重构之后先跑原来的测试。L02 的 53 个测试全部通过，才说明重构没有改变行为。

### [ ] ⑤ [prompts/judge_v1.yaml](../prompts/judge_v1.yaml) + [src/finagent/eval/judge.py](../src/finagent/eval/judge.py)（15 分钟）
- **知识点**：参考答案制的 prompt；`candidate_text` 故意不含推理过程；`threading.Lock` 保护计数器。
- **易错点**
  - 多个线程同时执行 `self.calls += 1`，结果可能少算：`+=` 是"读、加、写"三步，不是原子操作。
  - 裁判失败时返回 `error`，而不是默认判对或判错。

### [ ] ⑥ [src/finagent/eval/run.py](../src/finagent/eval/run.py)（20 分钟）
按顺序读：`run_eval` → `_row` → `build_summary` → `render_report` → `_verdict` → `compare_runs`。
- **知识点**
  - `mkdir(exist_ok=False)`：目录已存在就报错，绝不覆盖
  - `make_client` 参数：依赖注入，测试时换成假客户端
  - `git_info`：`subprocess.run` 调用 git，拿不到就返回 None
  - 一道题出错（API 异常）不影响其他题
- **易错点**
  - `compare_runs` 只比两边**共同**的题，并且在评测集哈希不一致时发出警告。
  - 报告里的 markdown 表格要转义 `|`、去掉换行。

### [ ] ⑦ [src/finagent/cli.py](../src/finagent/cli.py) 的 `eval_cmd` 和 `compare`（5 分钟）
- **知识点**：`@app.command("eval")`：函数名不能叫 `eval`（会遮盖 Python 内置函数），所以函数叫 `eval_cmd`，命令名单独指定为 `eval`。跑 test 时打印警告。

### [ ] ⑧ 测试（15 分钟）
[`tests/test_metrics.py`](../tests/test_metrics.py)、[`tests/test_evalsets.py`](../tests/test_evalsets.py)、[`tests/test_eval_run.py`](../tests/test_eval_run.py)
- **知识点**
  - `pytest.mark.parametrize` 把判分规则写成一张"输入 → 期望结果"的表
  - `tmp_path` fixture：pytest 提供的临时目录，测试不会污染真实的 `runs/`
  - 测试评测集文件本身：没有重复、划分正确、和 MANIFEST 一致
- **易错点**：判分规则的测试要覆盖边界（恰好等于容差、单位不同、数量级差 1000 倍），因为规则一错，之后所有实验结论都会跟着错。

## 第三轮 · 动手、实验、作业

### [ ] 运行命令（讲义 §9）
- `finagent eval` 默认跑 dev；跑 test 会打印警告。
- 读报告的顺序：指标和置信区间 → 按题型拆分 → 错误类型 → 逐题看几个错的。

### [ ] 读实验结果（讲义 §7）
- 对照 dev 的三份报告，找出 v2 答对、v3 拒答的题，看看 v3 拒答得有没有道理。
- 用 `finagent compare` 自己重现讲义里的比较表。

### [ ] 作业（讲义 §10）
- **作业 1（校准裁判）**：先盖住 `judge_verdict` 和 `judge_reasoning` 两列再标注。
- **作业 2（随机性）**：温度设 0 以后，比较"结果不同的题数"，而不只是准确率。
- **作业 3（改进裁判）**：换裁判之后，旧结果不能再和新结果直接比较。
- **作业 4（错误分析）**：只能看 dev。

## 最容易错的 10 件事（读完之后回来自查）

- [ ] 1. 根据 test 的结果去改系统。
- [ ] 2. 评测集没固定版本，或者被手工改过却没人知道。
- [ ] 3. 数值容差只用相对误差，忽略了标准答案的精度。
- [ ] 4. 只看准确率，不区分"答错"和"不答"。
- [ ] 5. 让裁判看推理过程，或者用和被测系统相同的模型当裁判。
- [ ] 6. 只看一致率，不看 kappa。
- [ ] 7. 两个系统各算各的区间来比较，而不是配对比较。
- [ ] 8. 把"不显著"当成"一样好"。
- [ ] 9. 在有未提交修改的代码上跑评测；或者跑多次只报告最好的一次。
- [ ] 10. 在一轮对比实验中途更换测量工具（裁判、容差、评测集）。
